## 1. 产品目标

### 目标一：让 easy-strm 从"纯整理工具"升级为"发现→获取→整理→播放"一站式工作台

当前 easy-strm 覆盖了"识别 → 整理 → STRM → 播放"后半段链路，但上游的"从哪里获取资源"始终是用户痛点。加入资源聚合功能后，用户的完整旅程将统一在一个工具内完成，无需在"找资源"和"整理资源"之间反复切换。

**衡量标准**：资源聚合功能上线后，全链路完成率（资源获取 → 整理 → STRM → Emby 播放）≥ 30%。

### 目标二：以 115 分享链接一键转存作为 MVP 突破口，建立差异化心智

竞品在 115 深度集成和 STRM 生成两个维度上均为空白。easy-strm 已具备 115 API 底座，将分享链接解析、目录浏览、一键转存、自动整理串联起来，可以形成竞争对手无法复制的闭环体验。

**衡量标准**：115 分享链接转存功能上线后，115 周活用户的转存使用率 ≥ 25%。

### 目标三：通过资源订阅（追剧/PT RSS）驱动用户留存，将产品使用频次从"按周批处理"提升至"按天主动使用"

纯整理工具天然低频，用户只有在"有新资源下载"时才打开 easy-strm。资源聚合（特别是追剧订阅和 RSS 监控）可为用户创建每日使用场景，将 WAO（周活跃整理完成数）提升 2-3 倍。

**衡量标准**：资源聚合上线 6 个月后，WAU 较当前基线增长 ≥ 100%。

## 2. 用户故事

### 故事一：老张的 115 全自动管道

> **"我收藏了一个 115 分享链接，里面有几百部 4K 电影。我想一键把他们都转存到我的 115，然后自动变成 STRM 文件，在 Emby 里就能看。"**

**场景**：老张在 PT 社区看到一个高质量的 115 分享链接（包含 500+ 部电影的目录），他目前的流程是：在 115 客户端打开链接 → 手动浏览 → 逐个勾选想转存的文件 → 等待转存完成 → 回到 easy-strm 手动添加媒体源 → 浏览 → 识别 → 整理 → 生成 STRM。全程耗时 30-60 分钟。

**理想体验**：老张在 easy-strm 的"资源聚合"页面粘贴 115 分享链接 → 系统解析目录树 → 老张勾选目标文件 → 点击"一键转存并整理" → 系统自动完成：秒传 → Watch 监听 → 自动整理 → STRM 生成 → Emby 刷新 → 通知完成。

**验收标准**：
- 粘贴 115 分享链接后，3 秒内展示完整目录树（含文件名、大小、类型）
- 支持全选 / 反选 / 按类型筛选（电影 / 剧集 / 其他）
- 点击"转存并整理"后进入后台任务，不阻塞界面
- 任务中心可查看转存进度（已完成 N / 总数 N，当前文件名）
- 转存完成后自动触发 Watch 整理（如已配置）或提示用户手动整理
- 支持秒传机制，已存在于目标目录的文件跳过上传

### 故事二：阿伟的追剧订阅

> **"我在豆瓣标记了十几部想看的剧，但总是忘记追踪它们的更新状态。希望 easy-strm 能帮我订阅这些剧，有更新时自动通知我，最好能自动下载。"**

**场景**：阿伟在豆瓣维护了一份"想看"片单，但每部剧的资源需要手动去 PT 站或资源站搜索。经常是"剧都完结了才想起来"，错过追剧体验。

**理想体验**：阿伟在 easy-strm 中输入豆瓣用户 ID → 系统解析想看列表 → 阿伟选择订阅目标剧集 → 系统定期扫描 PT RSS / 资源源 → 发现匹配资源 → 通知阿伟（或自动下载）→ 下载完成 → 自动整理 → Emby 中出现新剧集。

**验收标准**：
- 支持通过豆瓣用户 ID 导入想看列表
- 支持手动搜索并添加订阅（剧名 + 可选年份/季）
- 订阅列表展示每条订阅的状态（等待中 / 已命中 / 已下载 / 已整理）
- 订阅匹配基于 TMDB ID（确保不会匹配到同名错误资源）
- 支持设置质量偏好（1080p 优先 / 4K 优先 / 任意）
- 每周至少扫描一次（可配置频率）

**注意**：本故事中"自动下载"依赖 P1 的"下载器对接"能力，MVP 阶段可先实现"订阅 + 通知 + 手动触发下载"。

### 故事三：小陈的一键资源发现

> **"我听说有一部新出的电影很好看，但不知道怎么找资源。如果 easy-strm 能帮我搜索一下就好了。"**

**场景**：小陈想找一部 2024 年的国产电影，他在豆瓣上看到评分很高，但不知道哪里有资源。他打开 PT 站发现没注册，115 分享链接也找不到。

**理想体验**：小陈在 easy-strm 的"资源搜索"输入框输入电影名 → 系统从已配置的资源源（115 分享搜索 / PT RSS 等）返回匹配结果 → 小陈看到一条带"115 分享"标签的结果 → 点击"转存" → 资源立即开始转存到小陈的 115。

**验收标准**：
- 搜索支持电影名 / 剧集名（中文 / 英文 / IMDB ID）
- 搜索结果展示来源标签（115 / PT / 其他）
- 搜索结果展示基本信息（文件名、大小、清晰度标签）
- 无需配置即可使用（内置默认搜索源）
- 点击结果可直接发起转存或下载（取决于来源类型）

**优先级说明**：小陈是远期画像（P2），多源搜索在 ROI 评分中排 P3。MVP 阶段通过"115 分享链接转存 + 追剧订阅"覆盖小陈的部分需求，多源统一搜索留到后期。

### 故事四：影音发烧友的质量筛选

> **"同一个电影有好几个版本（1080p / 4K / HDR / 原盘），我想自动选择最好的那个。"**

**场景**：阿伟订阅了某部剧后，RSS 扫描发现同时有 3 个种子：1080p WEB-DL、4K HDR 和 4K 原盘。按照阿伟的偏好，系统应该自动选择 4K HDR 版本（如果可用），否则降级到 1080p。

**理想体验**：阿伟在设置中配置了质量偏好配置 → 系统命中多个资源时自动按规则排序 → 优先下载最佳版本 → 如果最佳版本下载失败，自动降级到次选。

**验收标准**：
- 支持按清晰度（4K / 1080p / 720p / 任意）设置优先级
- 支持按编码（HDR / DV / SDR）设置偏好
- 支持按来源（原盘 / WEB-DL / BluRay）设置偏好
- 多候选时自动应用规则，展示选中结果及理由
- 用户可手动覆盖自动选择

**优先级**：P2（锦上添花，核心功能稳定后追加）。

### 故事五：效率派的自动化全链路

> **"我希望 easy-strm 能成为我的媒体工厂：追剧订阅自动触发下载 → 下载完成自动整理 → 自动生成 STRM → Emby 自动刷新。我只需要偶尔检查一下任务中心看看有没有失败。"**

**场景**：老张已经配置好了追剧订阅、下载器（qBittorrent）、Watch 自动整理、Cron 定时 STRM。他期望日常零操作，只在收到失败通知或想看新剧时才打开 easy-strm。

**理想体验**：系统后台自动运转 → 新剧上线 → RSS 命中 → 下载器自动添加种子 → 下载完成后 Watch 检测到新文件 → 自动 TMDB 识别 → 自动重命名整理 → 自动 STRM 生成 → Emby 自动刷新 → Telegram 通知"《XXX》第 5 集已就绪"。

**验收标准**：
- 资源订阅 → 下载触发 ≤ 1 小时（取决于 RSS 扫描频率）
- 下载完成 → 整理完成 ≤ 10 分钟（取决于 Watch 轮询间隔）
- 整理完成 → STRM 生成 + Emby 刷新 ≤ 2 分钟
- 全链路失败时发送通知，包含失败环节和原因
- 任务中心可查看全链路每步的执行状态和耗时

**优先级**：P1 推荐（需要 P0 转存 + P1 订阅 + P1 下载器对接全部就绪后实现）。

## 3. 用户研究洞察

> 以下结论摘录自**用户研究报告**（瑞思 / UX Researcher，2026-07-24）。

### 3.1 用户画像与需求排序

| 画像 | 核心需求 | 资源聚合匹配度 | 优先级 |
| --- | --- | --- | --- |
| **老张（NAS 效率派）** | 补全自动化管道："下载 → 整理 → STRM" 全链路无人值守 | 极高 — 效率派已有自建脚本但维护成本高，资源聚合+自动整理可成为替代方案 | **P0** |
| **阿伟（影音发烧友）** | 质量发现 + 自动整理：PT 站 RSS 订阅、按质量偏好自动选择版本 | 高 — 影音发烧友有固定资源渠道但缺少自动化衔接 | **P0** |
| **小陈（入门整理者）** | "一键式"资源获取：不知道哪里找资源，也不想学复杂工具 | 高 — 入门用户完全无资源获取方案（80%），但需要极度简化的交互 | **P2（远期）** |

### 3.2 核心发现

**发现一：自动化需要"预览确认"安全阀门**

用户研究指出，用户对自动化的态度是"我信任自动化，但我不信任黑箱"。效率派需要自动化但要求透明（可查看日志、可随时介入）；入门者害怕自动化但一旦信任建立就深度依赖。

→ **PRD 设计原则**：资源聚合中的自动操作（转存、下载、整理）必须做到"可见、可解释、可撤销"。关键步骤（如批量转存选择、下载确认）提供预览 → 确认 → 执行的流程，不直接静默执行。

**发现二：用户需要的是"资源获取→整理→播放"闭环，而非独立搜索工具**

用户报告强调"整理完成不是终点，Emby 里看到效果才是"。资源聚合不应定位为"搜索引擎"或"资源发现工具"，而应定位为"给整理提供数据源的管道"。

→ **PRD 设计原则**：资源聚合模块始终锚定"获取 → 整理"的连接点，搜索结果/订阅命中后直接进入整理流程，不单独展示"搜索/浏览"结果后就结束。

**发现三：115 是 easy-strm 最大的差异化资产**

与竞品的对照分析显示，115 深度集成 + STRM 生成是 easy-strm 的核心差异点。在中文媒体服务器圈，115 网盘因其大容量和直链能力具有不可替代性。

→ **PRD 设计原则**：资源聚合以 115 为核心载体，"115 分享链接一键转存"作为 MVP 突破口。

### 3.3 8 个待验证假设（瑞思输出）

| 编号 | 假设 | 验证方式 | 建议在资源聚合功能中如何验证 |

### 4.3 差异化战略

**核心洞察**：8 个主流竞品在"115 深度集成"和"STRM 生成"两个维度上均为空白。easy-strm 应围绕这两个不可替代的能力构建资源聚合的价值主张。

**差异化定位**：**"给 easy-strm 的整理能力提供数据源"** —— 资源聚合不是独立搜索工具，而是 easy-strm 主链路的上游延伸。用户不是在 easy-strm 里"浏览资源"，而是"通过资源源发现问题，直接进入整理流程"。

**技术路径（竞析推荐）**：

| 阶段 | 能力 | 技术方案 | 依赖 |
| --- | --- | --- | --- |
| Phase 1 | 115 分享转存 | 115 API 分享链接解析 → 目录树展示 → 选择文件 → 秒传 | 现有 115 API 封装 |
| Phase 2 | Mikan RSS / PT RSS | 解析标准 RSS 2.0 / Mikan 格式 → 命中匹配 | RSS 解析库 |
| Phase 3 | Prowlarr API 复用 | 对接 Prowlarr 的索引器代理 API（如用户已部署 Prowlarr） | Prowlarr 服务（可选） |
| Phase 4 | TG Bot 集成 | 监听频道消息 → 解析资源信息 → 匹配订阅 | Telegram Bot API |

**核心原则**：
1. **索引器复用优于自建**：优先对接 Prowlarr 等成熟索引器，而非自建爬虫
2. **115 优先于通用 BT**：利用 115 的秒传和直链优势，形成独特壁垒
3. **定位为"给整理提供数据源"**：资源聚合页面不展示独立的"浏览/搜索"体验，始终锚定"获取 → 整理"连接点

- **35% 的高阶用户**可能从现有方案（自建脚本 / Sonarr 等）迁移到 easy-strm

### 6.1 P0：115 分享链接一键转存（RA-001）详细功能规格

#### 6.1.1 功能概述

用户将 115 网盘的分享链接粘贴到 easy-strm，系统解析出链接内的目录结构和文件列表，用户勾选目标文件后，系统通过 115 API 将文件秒传到用户自己的 115 目录中。转存完成后可选择自动触发 Watch 整理流程，最终生成 STRM 并在 Emby 中可播放。

#### 6.1.2 功能描述

**输入**：
- 115 分享链接（含密码，格式：`https://115.com/s/xxxxx?password=xxxx`）
- 仅分享链接，不含单个文件直链

**处理流程**：
1. 解析分享链接，提取 share_code 和 receive_code（密码）
2. 调用 115 API 获取分享目录的文件树
3. 展示交互式目录树供用户浏览和勾选
4. 用户选择目标 115 目录（用于转存目标）
5. 用户点击执行，系统逐文件调用 115 秒传 API
6. 秒传完成后（或批量完成后），触发可选后续动作

**输出**：
- 转存成功的文件出现在用户指定的 115 目录中
- 任务中心可查看转存任务状态
- （可选）自动触发 Watch 整理流程

## 9. Non-goals

以下事项**明确不属于**资源聚合功能的范围，以防止范围蔓延：

### 9.1 不提供内置内容源

easy-strm **不会**预置任何分享链接、PT 站地址、TG 频道、或资源索引。所有资源源由用户自行配置。easy-strm 定位为"工具"而非"内容平台"。

### 9.2 不建设自有的资源爬虫/索引器

easy-strm **不会**自行爬取第三方网站并建立资源索引。资源搜索和匹配依赖用户配置的资源源（RSS / Prowlarr / 分享链接）。多源统一搜索（RA-008）已评为 P3 暂缓。

### 9.3 不做下载器本身

easy-strm **不会**内置 BT 下载、HTTP 下载、或磁力链接下载能力。下载功能通过对接外部下载器（qBittorrent / Aria2）实现。

### 9.4 不做 PT 站账号管理或辅助工具

easy-strm **不会**帮助用户注册 PT 站、管理账号、刷流量（ratio boost）、或绕过 PT 站规则。只提供标准 RSS 订阅对接。

### 9.5 不做媒体资源的推荐/排行榜/发现Feed

easy-strm **不会**基于用户偏好、热门趋势、或社区评分推荐资源。这是内容平台的职责，不属于工具型产品范围。用户订阅的是"自己已知并明确想追踪的作品"。

### 9.6 不做文件分享/发布功能

easy-strm **不会**允许用户将自己的 115 文件生成为分享链接，也不提供任何形式的文件分发或共享功能。

### 9.7 不做移动端原生App

资源聚合功能与现有产品保持一致，仅提供 Web UI（通过 Docker 部署后浏览器访问）。不做 iOS/Android 原生应用。

### A. 术语表

| 术语 | 定义 |
| --- | --- |
| **115 分享链接** | 115 网盘用户生成的文件分享 URL，格式为 `https://115.com/s/xxxxx?password=xxxx` |
| **秒传** | 115 网盘的文件极速传输机制：如果目标用户网盘中已存在相同 hash 的文件，则无需真实上传，直接关联即可 |
| **STRM** | 流媒体重定向文件，包含媒体文件的实际播放 URL，Emby/Jellyfin 读取后可将远程文件（如 115 云文件）作为本地媒体库内容播放 |
| **Watch** | easy-strm 的自动监控功能：监控指定目录，检测到新文件时自动触发识别和整理流程 |
| **Cron STRM** | easy-strm 的定时 STRM 生成功能：按 Cron 表达式定时扫描指定目录并生成 STRM 文件 |
| **RSS** | Really Simple Syndication，在此场景中指 PT 站或资源站提供的种子更新 Feed |
| **WAO** | Weekly Active Organization，周活跃整理完成数：每周成功完成"资源获取→整理→STRM"全链路的用户数 |
