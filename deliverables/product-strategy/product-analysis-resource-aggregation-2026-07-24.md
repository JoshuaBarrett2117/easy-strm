## 一、产品现状分析

### 1.1 当前产品定位

easy-strm 是面向个人媒体服务器（Emby/Jellyfin/Plex）用户的文件整理与 STRM 生成工作台。主链路为：

```
媒体源接入 → 文件浏览与选择 → TMDB 自动/手动识别 → 重命名与整理 → 元数据刮削(可选) → STRM 生成 → Emby 刷新
```

三条差异化护城河：
1. **115 云盘独家原生整合** — 市面上唯一支持 115 深度集成的一站式工具
2. **STRM 直链生成** — 竞品均无此能力，"云端存储 + 本地流化"架构节省磁盘空间
3. **部署简洁** — 单一 Docker Compose（3 容器）vs 竞品 5-7 个容器

### 1.2 功能使用分布（推演）

| 层级 | 使用占比 | 核心功能 |
|------|----------|----------|
| 🔥 高热（>80%） | 文件浏览、TMDB 识别、重命名/整理、仪表盘 |
| 🟡 中热（40-80%） | STRM 生成（~70%）、任务中心（~55%）、Emby 刷新（~50%） |
| 🔵 低热（15-40%） | 媒体源管理、Watch（25-35%）、Cron（20-30%）、整理规则 |
| ❄️ 冷功能（<15%） | 系统日志、网络测试、缓存管理 |

> 两个关键信号：自动化采纳率偏低（Watch 35%、Cron 30%），反映配置复杂度门槛；STRM 是用户分水岭（30% 用户可能无法跨越概念门槛）。

### 1.3 用户增长漏斗（推演）

```
发现 → 了解(30-45%) → 部署(50-65%) → 首次整理(40-55%) → 二次整理(55-70%) → 周活(35-50%) → 日活(10-20%)
                                                                                      ↑
                                                                            资源聚合最大增量区域
                                                                            （+15-20pp 提升）
```

**最大流失环节**：部署→首次整理（仅 40-55% 转化），根因是新手引导缺失和操作路径不明确。**加入资源聚合后**，整体激活率预估从 ~3% 提升至 ~6%。

## 二、用户需求分析

### 2.1 需求强度排序

## 六、关键架构决策

### 6.1 定位原则

> 资源聚合不是"另一个搜索引擎"，而是**"给整理提供数据源"的辅助模块**。

- 不做独立资源平台（不预置内容源、不推荐、不做分享）
- 不做替代 Sonarr/Radarr 的通用下载器
- 索引器复用优于自建（Prowlarr API > 自建爬虫）
- 所有自动操作必须有"预览确认"安全阀门

### 6.2 信息架构嵌入

资源聚合嵌入到现有**文件工作台**中，不作为一级模块：

```
仪表盘
└── [NEW] "下载中资源"卡片

文件工作台
├── 已有文件浏览/整理
├── [NEW] "添加资源"入口
│   ├── 115 分享转存
│   ├── 追剧订阅
│   └── 订阅源管理
└── 任务中心
    └── [NEW] 下载任务 + 转存任务（统一队列）
```

### 6.3 与现有链路的衔接

资源聚合不新建独立的执行管道，而是**复用 Watch 基础设施**：

```
用户粘贴 115 分享链接
  → 解析 + 选择文件 + 目标目录
  → 发起转存任务（任务中心跟踪）
  → 转存完成 → 自动创建预设 Watch 规则（"标准自动整理"模板）
  → Watch 触发：TMDB 识别 → 重命名 → 整理
  → 整理完成 → 触发 STRM 生成（如已配置）
  → STRM 完成 → Emby 刷新（如已配置）
  → 用户打开 Emby → 新资源已在海报墙
```

## ⚠️ 待确认 / 假设 / Non-goals

### 待确认（法务）

- LEGAL-001：工具仅搜索公开分享链接的版权责任边界
- LEGAL-002：用户协议中的"用户自担版权风险"条款有效性
- LEGAL-003：PT 站种子/RSS 订阅的合规边界
- LEGAL-004：是否需要引入 DMCA / 权利方投诉处理机制

### 待确认（技术）

- TECH-001：115 分享链接解析（SHA1/提取码/URL 格式）的逆向稳定性
- TECH-002：115 秒传 API 的调用频率限制（单日上限？）
- TECH-003：Mikan Project RSS 的站点稳定性与去重逻辑
- TECH-004：Prowlarr API 的 Torznab 协议兼容性验证
- TECH-005：qBittorrent/Aria2 API 权限模型与容器网络通信方案

### 已明确的 Non-goals

| # | 不做内容 | 原因 |
|---|----------|------|
| 1 | 不提供内置/预置内容源（频道、站点列表） | 版权风险隔离 |
| 2 | 不自建内容爬虫或索引器 | 复用 Prowlarr/Jackett 生态 |
| 3 | 不做独立的下载器（不内置 qBit/Transmission） | 对接用户已有下载器 |
| 4 | 不做 PT 站账号管理（上传量/ratio 监控） | 专注整理，不涉 PT 运营 |
| 5 | 不做内容推荐/个性化算法 | 风险高、投入大、与定位不符 |
| 6 | 不做资源分享/分发功能 | 版权红线 |
