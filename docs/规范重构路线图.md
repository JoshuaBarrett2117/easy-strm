# 规范重构路线图

- 更新日期：2026-05-15
- 执行者：Codex
- 适用依据：根目录 `AGENTS.md`、`docs/开发与测试.md`、当前代码扫描结果
- 目标：让项目逐步符合分层清晰、设计模式适度、SOLID 友好、测试可验证的开发规范

## 1. 总体结论

当前项目已经具备可运行的全栈结构，后端有 `controller/service/dao/domain` 分层，前端有 `views/components/utils/api` 的基本组织，Go 测试和前端构建也已有基础。但从规范角度看，项目仍处在“功能成型但架构债务明显”的阶段。

优先级最高的问题不是视觉或局部命名，而是：

1. 存在占位实现和“假成功”返回，接口契约不可信。
2. Controller 直接依赖 DAO，业务规则没有完全收束到 Service。
3. 大文件和长函数过多，单一职责原则不足。
4. Go 格式化状态不一致，基础质量门禁未完全固化。
5. 前端部分页面直接调用底层 `request`，接口契约分散在页面层。
6. 前端缺少单元测试，主要依赖构建和 E2E 脚本。

本路线图按“先消除行为风险，再整理分层，再拆解复杂度，最后补齐测试与文档”的顺序推进。

### 2.2 占位与假成功风险

以下代码违反“禁止占位实现”和“接口返回必须真实表达执行结果”的规范：

- `easy-strm/internal/service/file_operation_service.go`：115 云盘移动标注 TODO，但返回成功。
- `easy-strm/internal/service/file_operation_service.go`：115 云盘复制标注 TODO，但返回成功。
- `easy-strm/internal/service/file_operation_service.go`：115 云盘删除标注 TODO，但返回成功。
- `easy-strm/internal/controller/strm_controller.go`：增量 STRM 生成仍为未实现占位响应。
- `easy-strm/internal/service/media_source_service.go`：存在“占位结果由 Controller 填充”的注释，说明 Service 与 Controller 职责倒置。

这些问题必须优先处理，因为它们会误导前端、任务中心和测试脚本。

### 2.3 分层风险

Controller 直接依赖 DAO 的位置包括：

- `internal/controller/log_controller.go`
- `internal/controller/media_category_controller.go`
- `internal/controller/media_library_controller.go`
- `internal/controller/media_source_controller.go`
- `internal/controller/pending_media_controller.go`
- `internal/controller/settings_controller.go`
- `internal/controller/tmdb_controller.go`

规范目标是：

```text
controller -> service -> dao -> database/cache
```

当前部分链路实际是：

```text
controller -> dao
controller -> service + dao
```

这会导致参数校验、业务归一化、缓存更新、响应拼装散落在 Controller 中，后续修改接口时更容易出现漏改。

### 2.4 前端 API 封装风险

多数新媒体相关 API 已经进入 `src/utils/api/*`，但仍有页面直接调用底层 `request(...)`：

- `easy-strm-front/src/views/Cloud115.vue`
- `easy-strm-front/src/views/StrmConfig.vue`

规范目标是页面只调用业务 API 函数，例如：

```text
views/components -> utils/api/cloud115.js
views/components -> utils/api/strm.js
views/components -> utils/api/task.js
```

页面不应直接维护 URL、HTTP 方法和查询参数拼装。

### 2.5 格式化与基础质量

`gofmt -l` 当前列出多批 Go 文件，说明格式化状态不一致。重构前应先单独做一次格式化提交或格式化阶段，避免后续业务 diff 被格式噪音淹没。

当前可见测试资产：

- 前端 `.test.*` / `.spec.*` 文件：0 个。
- Playwright / E2E 脚本：23 个。
- `package.json` 暴露的 E2E 命令：3 个。

## 3. 重构总原则

1. 先修真实行为，再拆结构；不能在假成功和占位逻辑存在时做大规模抽象。
2. 每一阶段只解决一类问题，保持 diff 可读、测试可定位。
3. Controller 只做 HTTP 适配，业务流程沉入 Service。
4. DAO 只做存储访问，不向上泄露前端响应结构。
5. 前端页面只组合组件和调用业务 API，不直接拼接口 URL。
6. 设计模式只在变化点明确时使用，不制造空接口。
7. 每次重构必须有测试或本地验证命令证明行为未退化。
8. 不追求一次性“完美架构”，按风险收益顺序渐进收敛。

## 4. 目标架构

### 4.1 后端目标形态

```text
main.go
  -> bootstrap / router registration
  -> controller
  -> service
  -> dao
  -> PostgreSQL / Redis / external clients
```

推荐逐步形成以下边界：

- `controller`：HTTP 参数、状态码、响应包装。
- `service`：业务用例、策略选择、任务推进、错误归一化。
- `dao`：数据查询、写入、事务、缓存访问。
- `client/adapter`：外部平台适配，例如 115、TMDB、Emby、文件系统。
- `domain`：领域模型、枚举、请求响应 DTO、纯规则。
- `bootstrap` 或等价装配模块：集中依赖构造和路由注册，替代巨大的 `auth.go` 装配函数。

### 4.2 前端目标形态

```text
views
  -> components
  -> composables
  -> utils/api
  -> request
```

推荐逐步形成以下边界：

- `views`：页面布局和跨组件工作流。
- `components`：表格、弹窗、表单、结果展示等局部交互。
- `composables`：轮询、表单状态、媒体源选择、任务刷新等可复用状态逻辑。
- `utils/api`：后端接口契约。
- `utils/ui`：统一消息、确认框和 UI 辅助能力。

## 5. 分阶段重构计划

### 阶段 0：建立干净基线

目标：减少后续 diff 噪音，确保当前状态可验证。

任务：

1. 单独执行 Go 格式化，避免和业务重构混在一起。
2. 确认 `go test ./...`、`go vet ./...`、`npm run build` 均通过。
3. 记录当前 E2E 可运行前置条件，包括后端地址、前端地址、测试数据要求。
4. 清点 `docs/` 中一次性测试报告，决定是否迁移到 `debug/` 或保留索引。

验收：

- `gofmt -l` 无输出。
- 后端测试和前端构建通过。
- 没有业务逻辑变更。

### 阶段 1：消除占位实现与假成功

目标：让接口结果可信，先修最容易误导用户和测试的行为风险。

任务：

1. 处理 115 文件移动、复制、删除。
2. 如果当前 SDK 不支持真实操作，接口必须返回明确“不支持”或“未实现”，不能返回成功。
3. 为 115 文件操作补 Service 测试，覆盖不支持能力、SDK 错误、成功路径。
4. 处理 STRM 增量生成占位逻辑：实现真实增量，或改为明确错误响应并同步前端隐藏/禁用入口。
5. 清理 `media_source_service.go` 中“由 Controller 填充”的职责倒置。

建议设计模式：

- Adapter：封装 115 文件操作能力，内部适配具体 SDK。
- Strategy：本地文件操作和 115 文件操作分离为不同策略。

验收：

- 所有涉及文件操作的接口不再返回假成功。
- 前端能展示真实失败原因。
- `go test ./...` 通过。
- 相关文件操作测试覆盖本地与 115 分支。

### 阶段 2：Controller 去 DAO 化

目标：恢复规范分层，让 Controller 只做 HTTP 适配。

任务：

1. 为媒体分类新增 `MediaCategoryService`，迁移 `media_category_controller.go` 中的 DAO 调用。
2. 为待处理媒体新增或完善 `PendingMediaService`，迁移 `pending_media_controller.go` 中的 DAO 调用。
3. 为媒体库列表新增查询 Service，迁移 `media_library_controller.go` 中的数据组装。
4. 将 `tmdb_controller.go` 中缓存写入、详情提取、识别保存流程下沉到 `TmdbService`。
5. 将 `settings_controller.go`、`log_controller.go` 的配置读取通过 Service 抽象。
6. 清理 Controller 中 `internal/dao` import，测试文件除外。

建议设计模式：

- Service Layer：每个 Controller 依赖明确业务 Service。
- Repository / DAO：存储访问只留在 DAO 或 Service 内部。

验收：

- `rg -n "internal/dao|dao\\." easy-strm\\internal\\controller -g "*.go"` 只允许测试或极少数装配例外。
- Controller 单测仍覆盖参数错误、成功响应、关键失败分支。
- `go test ./...` 通过。

### 阶段 3：拆分后端巨石流程

目标：降低单文件和长函数复杂度，让变化点可定位。

优先顺序：

1. `organize_service.go`
2. `db.go`
3. `auth.go`
4. `115client.go`
5. `cron.go`
6. `rename_service.go`
7. `scrape_service.go`

拆分建议：

- `organize_service.go` 拆为扫描、预览、执行、分类策略、目标路径构建、115 专用操作、本地专用操作。
- `db.go` 保留启动兼容入口，迁移表初始化和旧 DAO 风格函数到 `internal/dao` 或迁移脚本。
- `auth.go` 拆出认证路由、业务路由、依赖装配。
- `115client.go` 拆出认证、文件浏览、离线/导出、秒传、目录树解析。
- `cron.go` 将定时触发和具体业务执行解耦。
- `rename_service.go` 拆出文件名解析、模板渲染、冲突处理、执行器。
- `scrape_service.go` 拆出 NFO 构建、图片处理、兜底数据构建。

建议设计模式：

- Strategy：整理操作模式、冲突策略、媒体源类型。
- Pipeline：识别 -> 预览 -> 执行 -> 刮削 -> STRM。
- Factory：根据媒体源类型创建文件操作器。
- Template Method：本地和 115 整理流程共享骨架，差异步骤由策略实现。

验收：

- 单个新增文件职责明确。
- 原有公开方法签名尽量稳定，减少一次性连锁改动。
- 每拆一块补对应测试，确保行为不变。
- 长函数数量持续下降。

### 阶段 4：前端 API 与状态逻辑收敛

目标：页面只表达工作流，不维护底层接口细节。

任务：

2. 将 `StrmConfig.vue` 中的直接 `request(...)` 迁移到 `utils/api/strm.js`、`utils/api/task.js`、`utils/api/cloud115.js` 或新增 `utils/api/cron.js`。

5. 拆分大业务组件：`FileBrowser.vue`、`MediaSourceList.vue`、`OrganizeDialog.vue`。

```text

src/utils/api/cron.js
src/components/cloud115/*
src/components/strm/*
```

验收：

### 阶段 5：测试体系补强

## 6. 后续执行顺序建议

推荐按以下顺序开工：

1. 阶段 0：格式化和验证基线。
2. 阶段 1：115 文件操作假成功、STRM 增量占位。

## 8. 风险与回滚策略

### 8.1 高风险区域

- 115 文件操作、登录、导出目录树、秒传。
- 自动整理、任务中心、失败分类、重试。
- STRM 全量生成和后续增量生成。
- TMDB 识别、手动修正、缓存回流。
- 前端轮询和弹窗关闭行为。

### 8.2 回滚策略

- 每个阶段单独提交，避免混合格式化、业务修复和架构拆分。
- 大文件拆分时先移动纯函数或私有 helper，再移动状态ful 流程。
- 对外接口路径和响应结构非必要不改；必须改时同步前端 API 封装和测试。
- 每次拆分前记录当前测试命令结果，拆分后运行同一组命令对比。

## 9. 完成判定

当以下条件满足时，可认为本轮规范重构完成：

- 不存在返回假成功的占位业务接口。
- Controller 不直接依赖 DAO，测试文件和装配例外除外。
- `gofmt -l` 无输出。
- 主要巨石文件已拆出清晰子模块，新增代码职责单一。
- 前端业务页面不直接调用底层 `request(...)`。
- 后端 `go test ./...`、`go vet ./...`、前端 `npm run build` 稳定通过。
- 媒体整理、STRM、任务中心至少有一组稳定 E2E 回归入口。
- `docs/开发与测试.md` 和 `docs/产品与架构.md` 已同步最终状态。
