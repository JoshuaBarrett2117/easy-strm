## 第一部分：用户研究计划

### 1. 研究背景

#### 1.1 产品定位

easy-strm 是一款面向个人媒体库的文件整理与 `.strm` 生成工作台，核心流程为：

```
媒体源接入 → 文件浏览与选择 → TMDB 自动/手动识别 → 重命名与整理预览
→ 移动/复制/链接 → 可选元数据刮削 → STRM 生成 → Emby 刷新与任务追踪
```

产品聚焦于"浏览、识别、整理、刮削、STRM、追踪"六大环节，不承担资源聚合、下载器管理或完整媒体资产治理平台职责。

#### 1.2 为什么要做用户研究

- **产品已历经功能收敛**（2026-07-23 下线媒体资产台账、同步索引、入库流水线等低频功能），需要验证当前功能范围是否精准匹配核心用户需求。
- **主链路复杂度高**：从媒体源接入到 STRM 生成涉及 7+ 个步骤，任一环节的摩擦都可能造成用户流失。
- **用户群体特殊**：面向个人媒体服务器（Emby/Jellyfin/Plex）用户，该群体技术能力参差、使用场景多样，缺乏系统性用户洞察。
- **竞品生态活跃**：存在多种替代方案（手动脚本、其他 STRM 工具、NAS 套件），需要明确 easy-strm 的差异化价值。

#### 1.3 研究范围

| 维度 | 覆盖范围 |
| --- | --- |
| **功能模块** | 媒体源管理、文件浏览与选择、TMDB 识别、重命名与整理、STRM 生成、任务追踪、自动整理（Watch/Cron） |
| **用户触点** | 仪表盘、任务中心、文件工作台、STRM 配置、115 云管理、整理规则、系统设置、系统日志、网络测试、缓存管理 |
| **排除范围** | 媒体资产台账、同步索引、入库流水线、多用户权限（已下线或尚未支持） |

### 2. 研究目标与核心问题

#### 2.1 首要研究目标

| 编号 | 研究目标 | 业务关联 |
| --- | --- | --- |
| G1 | 理解目标用户的核心使用场景与媒体库管理习惯 | 产品定位验证 |
| G2 | 评估当前主链路（接入→整理→STRM）的可用性与效率 | 体验优化 |
| G3 | 识别用户在使用各环节中的关键痛点和放弃原因 | 留存提升 |
| G4 | 验证"文件工作台"作为核心入口的认知模型是否清晰 | 信息架构 |
| G5 | 了解用户对自动化整理（Watch/Cron）的理解与信任度 | 功能采纳 |

#### 2.2 核心研究问题

围绕产品主链路，提出以下五个层次的研究问题：

**层次一：用户画像与场景**

- RQ1.1：easy-strm 典型用户的媒体库规模、类型分布和使用频率是怎样的？
- RQ1.2：用户通常在什么情境下产生"整理媒体库"的需求？（如新下载一批资源后、媒体库混乱到临界点、换 NAS 设备等）
- RQ1.3：用户当前如何解决媒体整理问题？使用哪些工具组合？

**层次二：认知与心智模型**

- RQ2.1：用户如何理解"媒体源""整理规则""分类策略"等核心概念？
- RQ2.2：用户期望的产品工作流是怎样的？与实际流程的差距在哪里？
- RQ2.3：新用户首次使用时，能否独立完成"添加媒体源 → 浏览文件 → 自动识别 → 整理执行"的闭环？

**层次三：交互与可用性**

- RQ3.1：文件浏览（本地/115）的搜索、筛选、分页体验是否高效？
- RQ3.2：TMDB 自动识别的准确率是否满足用户预期？手动修正流程是否顺畅？
- RQ3.3：整理预览→执行的反馈是否清晰？"冲突策略"是否被正确理解？
- RQ3.4：任务中心的进度展示、取消、重试机制是否满足用户掌控感？

**层次四：自动化与信任**

- RQ4.1：用户对 Watch 自动整理和 Cron 定时 STRM 的期望行为是什么？
- RQ4.2：自动整理失败时，用户期望收到怎样的通知和处理方式？
- RQ4.3：什么是用户能够接受的"自动操作"边界？哪些环节必须人工确认？

**层次五：价值感知与竞品选择**

- RQ5.1：与手动脚本、其他 STRM 工具、NAS 套件相比，用户为什么选择或不选择 easy-strm？
- RQ5.2：用户认为 easy-strm 最不可替代的功能是什么？最"鸡肋"的功能是什么？

### 3. 研究方法

采用**混合研究方法**（Mixed Methods），定性为主、定量为辅，通过方法三角互证提升结论可靠性。

#### 3.1 方法矩阵

| 方法 | 类型 | 样本量 | 目的 | 回答的研究问题 |
| --- | --- | --- | --- | --- |
| **深度访谈** | 定性 | N=15-20 | 深入理解用户场景、心智模型、使用习惯 | RQ1.1-1.3, RQ2.1-2.3, RQ5.1-5.2 |
| **可用性测试** | 定性+定量 | N=10-12 | 观察用户执行核心任务时的行为、错误和效率 | RQ3.1-3.4 |
| **问卷调查** | 定量 | N≥200 | 量化用户画像分布、功能使用频率、满意度 | RQ1.1, RQ4.1-4.3 |
| **行为数据分析** | 定量 | 全量用户 | 补充实际使用数据，发现隐藏行为模式 | RQ3.1, RQ3.3, RQ4.2 |
| **竞品体验走查** | 定性 | 3-5 款竞品 | 建立行业基准，识别差异化机会 | RQ5.1-5.2 |

#### 3.2 方法选择的理由

- **深度访谈优先**：easy-strm 目标用户群体小众（个人媒体服务器用户），定性深访比大规模问卷更能揭示真实需求和行为动因。
- **可用性测试聚焦主链路**：产品的核心价值在于"媒体整理效率"，任务完成率和错误率是衡量成功的硬指标。
- **问卷作为定量补充**：通过社区（Emby 中文论坛、NAS 玩家群、V2EX、Reddit r/selfhosted 等）触达更广泛用户，验证定性发现的代表性。
- **行为数据分析降低回忆偏差**：用户自述行为与实际操作常有差距，服务端日志和前端埋点可提供客观校验。

#### 3.3 偏差控制策略

| 偏差类型 | 控制措施 |
| --- | --- |
| **选择偏差** | 分层抽样：按技术能力（高/中/低）、媒体库规模、使用时长分层，确保各群体均有代表 |
| **社会期望偏差** | 访谈开场强调"没有正确/错误答案，我们想了解真实体验"；采用行为导向提问（"请展示你最近一次整理的过程"而非"你觉得整理功能好用吗"） |
| **观察者效应（霍桑效应）** | 可用性测试前安排 5 分钟预热任务，让参与者适应"边做边说"的模式 |
| **确认偏差** | 预注册研究假设；分析时先列出不支持假设的证据；双人独立编码 |
| **回忆偏差** | 尽可能请求用户展示实际操作或截图；结合行为数据进行交叉验证 |

### 4. 参与者画像与招募

#### 4.1 目标参与者定义

easy-strm 的目标用户分为三个核心细分群体：

| 用户细分 | 特征描述 | 预估占比 |
| --- | --- | --- |
| **"影音发烧友"** | 拥有大规模媒体库（1000+ 部），使用 Emby/Plex/Jellyfin，关注刮削质量和命名规范，常混迹于相关社区 | 40% |
| **"NAS 效率派"** | 技术能力强，重视自动化，倾向于用脚本和工具链解决问题，对 UI 要求不高但重视可靠性 | 35% |
| **"入门整理者"** | 媒体库规模中等（100-500 部），刚接触媒体服务器不久，需要引导式操作，易被复杂配置劝退 | 25% |

#### 4.2 筛选标准

**入选条件**（必须同时满足）：

- 当前正在使用或曾经使用过 Emby / Jellyfin / Plex 中至少一种
- 拥有至少 50 部以上的个人媒体文件（电影或剧集）
- 在过去 3 个月内进行过至少一次媒体文件整理操作
- 对计算机基本操作（文件系统、路径、命令行）有一定了解

**排除条件**：

- 从事媒体整理工具或竞品开发工作的从业者（避免专业视角干扰）
- 过去 6 个月内参与过类似用户研究（避免疲劳效应）

**分层配额**（用于访谈和可用性测试）：

| 维度 | 配额要求 |
| --- | --- |
| 技术能力 | 高（能独立部署 Docker）：5 人；中（会用 NAS 套件）：5 人；低（需要教程指导）：5 人 |
| 媒体库规模 | 大型（1000+）：5 人；中型（100-1000）：5 人；小型（50-100）：5 人 |
| easy-strm 使用经验 | 新用户（首次使用 ≤ 2 周）：5 人；普通用户（1-3 个月）：5 人；重度用户（3 个月+）：5 人 |

#### 4.3 招募渠道

| 渠道 | 预计覆盖 | 招募方式 |
| --- | --- | --- |
| Emby 中文社区 / QQ 群 / Telegram 群 | 影音发烧友 | 发布招募帖，提供研究说明和报名表单 |
| V2EX / NAS 玩家论坛 / Chiphell | NAS 效率派 | 同上 |
| Reddit r/selfhosted / r/emby / r/jellyfin | 海外 + 中文双语用户 | 英文招募帖，注明支持远程视频访谈 |

| 社交媒体（即刻、少数派） | 入门整理者 | 内容合作 + 招募海报 |

#### 4.4 激励方案

| 研究类型 | 时长 | 激励 |

### 5. 研究协议与执行计划

#### 5.1 时间线

```
Week 1    研究设计与材料准备
          - 撰写访谈提纲、可用性测试任务脚本、问卷设计
          - 准备测试环境（含隔离测试数据的 easy-strm 实例）
          - 预测试（Pilot test）N=2，修正材料

Week 2-3  数据收集
          - 深度访谈：每日 2-3 场，持续 2 周
          - 可用性测试：Week 2 后半段开始，每日 1-2 场
          - 问卷发放：Week 1 末发出，Week 3 截止
          - 行为数据导出：Week 3 末

Week 4    分析与报告
          - 访谈转录与编码（NVivo 或手工编码）
          - 可用性测试数据统计（任务完成率、耗时、错误率）
          - 问卷数据分析（描述性统计 + 交叉分析）
          - 三角互证与洞察提炼
          - 撰写研究报告

Week 5    汇报与跟进
          - 向产品/开发团队汇报
          - 整理可执行改进清单
          - 建立追踪机制
```

#### 5.2 深度访谈提纲（核心结构）

**开场（5 分钟）**
- 自我介绍、研究目的说明
- 录音/录像知情同意
- 强调"无对错之分，想听真实体验"

**热身（5 分钟）**
- "请简单介绍一下你的媒体库——大概有多少部电影/剧集？用什么媒体服务器？"
- "你平时怎么看影视内容？设备、频率、场景？"

**核心访谈（30 分钟）**

| 主题 | 示例问题 |
| --- | --- |
| 整理习惯 | "你上一次整理媒体文件是什么时候？是因为什么触发的？"<br>"能展示一下你现在的文件目录结构吗？你是如何命名的？" |
| 工具使用 | "除了媒体服务器，你还用哪些工具管理媒体文件？"<br>"你尝试过 STRM 方案吗？为什么用/不用？" |
| 痛点探索 | "在当前的整理流程中，最让你头疼的环节是什么？"<br>"你曾经因为什么问题放弃过某个工具或流程？" |
| 自动化期望 | "你理想中的媒体整理应该是怎样的？"<br>"如果有一个工具能自动完成整理，你最担心什么？" |
| easy-strm 体验（如有使用） | "你第一次使用 easy-strm 时，最困惑的是什么？"<br>"哪个功能你用得最多？哪个功能你几乎不用？为什么？" |

**收尾（5 分钟）**
- "如果你能给 easy-strm 团队提一个建议，会是什么？"
- 补充问题与感谢

#### 5.3 可用性测试任务设计

测试环境：预装 easy-strm 的 Docker 实例，内含 100+ 个测试用媒体文件（多种命名格式、混合语言）。

**任务脚本**：

| 任务 | 场景描述 | 成功标准 | 测量指标 | 对应功能 |
| --- | --- | --- | --- | --- |
| T1 | "你刚下载了一批电影到本地目录 /downloads，请将它们添加为媒体源，并浏览这些文件" | 创建媒体源并成功浏览到文件列表 | 完成率、耗时、错误次数 | 媒体源 + 文件浏览 |
| T2 | "请对这些文件进行自动 TMDB 识别，对识别错误的文件手动修正" | 所有文件匹配正确 TMDB ID | 完成率、耗时、操作步数 | TMDB 识别 |
| T3 | "按照默认模板重命名这批文件，并选择'复制'模式整理到 /media/movies" | 预览显示正确新文件名，执行成功 | 完成率、耗时、冲突策略理解度 | 重命名 + 整理 |
| T4 | "为这批电影生成 STRM 文件，并配置 Emby 刷新" | STRM 生成并触发 Emby 刷新 | 完成率、耗时 | STRM + Emby |
| T5 | "设置一个自动整理规则：当 /downloads 有新文件时自动识别、重命名并整理" | Watch 规则正确创建并启动 | 完成率、信心评分（1-5） | Watch 自动化 |
| T6 | "找到刚才整理的 STRM 生成任务，查看它的进度和结果" | 在任务中心定位到该任务并理解状态 | 找到率、耗时 | 任务中心 |

**测试后评估**：

- 系统可用性量表（SUS）：10 题标准 SUS
- 单项简易评估（SEQ）：每个任务后 "这个任务的难度如何？"（1-7 分）
- 净推荐值（NPS）："你有多大可能向朋友推荐 easy-strm？"（0-10）
- 开放式反馈："最满意的 3 点和最不满意的 3 点"

### 6. 数据分析框架

#### 6.1 定性数据分析

采用**主题分析法**（Thematic Analysis），六步流程：

1. **熟悉数据**：反复阅读访谈转录，记录初步印象
2. **初始编码**：逐行开放编码，不预设类别
3. **搜索主题**：将编码归类为潜在主题
4. **审查主题**：检查主题内部一致性和主题间区分度
5. **定义与命名**：为每个主题写精确定义和范围说明
6. **撰写报告**：用参与者原文支撑主题论述

**编码框架示例**（可随实际数据调整）：

```
一级编码                    二级编码
───────────────────────────────────────────
整理触发场景                手动触发 / 定期清理 / 换设备
命名困扰                    格式不统一 / 多版本 / 合集分类
TMDB 匹配问题               误识别 / 冷门资源无结果 / 动画特辑难区分
自动化担忧                  误操作 / 不可逆 / 通知不及时
工具切换原因                效率低 / 不稳定 / 学习成本高
```

#### 6.2 定量数据分析

| 数据来源 | 分析方法 |
| --- | --- |
| 问卷 | 描述性统计（均值、中位数、分布）；交叉分析（技术能力 × 功能使用频率、媒体库规模 × 满意度） |
| 可用性测试 | 任务完成率（二项检验）、平均任务耗时（与基准对比）、错误率；SUS 总分（标准化为 0-100） |
| 行为数据 | 漏斗分析（各步骤转化率）、路径分析（实际点击流 vs 理想路径）、功能使用频率排名 |

#### 6.3 三角互证策略

- 访谈中提到的痛点是否存在行为数据佐证？（如用户说"整理预览太慢"→ 查看整理预览接口平均响应时间）
- 问卷中的满意度分布是否与可用性测试 SUS 得分方向一致？
- 不同用户细分群体的发现是否收敛或出现有意义的差异？

#### 10.3 需求洞察的三个核心主题

**主题一："我信任自动化，但我不信任黑箱"**

几乎在所有用户细分中，对"自动化"的需求和恐惧并存。效率派需要自动化但要求透明（可查看日志、可随时介入）；入门者害怕自动化但一旦信任建立就依赖它。

→ **设计启示**：自动化功能必须做到"可见、可解释、可撤销"。每一步自动操作的决策都应有日志记录，失败时提供可操作的错误信息，关键步骤提供"预览→确认→执行"的安全阀门。

**主题二："整理完成不是终点，Emby 里看到效果才是"**

用户的最终目标是"在 Emby/Jellyfin/Plex 里看到整齐的海报墙"，而非"完成整理任务"。当前产品在整理完成和 Emby 验证之间的体验断裂——用户需要手动切换工具、手动刷新、手动确认。

→ **设计启示**：构建"整理 → STRM → Emby 刷新 → 效果预览"的闭环体验。任务完成后提供一键跳转到 Emby 对应媒体库的快捷方式；可选自动触发 Emby 刷新并展示刷新结果。

**主题三："我知道我有一堆文件，但我不知道它们是什么"——信息可见性不足**

用户在面对批量未整理文件时，最大的认知负担是"哪些识别了、哪些没识别、哪些识别可能错了"。当前界面缺少"整理状态总览"式的信息层级。

→ **设计启示**：在文件工作台增加"整理状态看板"——概览视角下显示已识别/未识别/待确认的文件数量和占比，支持一键筛选和处理特定状态的文件。

#### 11.1 竞品格局

| **Sonarr/Radarr** | 自动化工具 | 全自动媒体管道、生态丰富 | 配置复杂、无中文优化、不友好 | 中文 UX、简化配置、115 原生支持 |
| **NAS 套件（群晖 Video Station 等）** | 集成方案 | 开箱即用、与 NAS 深度整合 | 刮削能力弱、不灵活、封闭 | 灵活性、跨 NAS 平台、STRM 方案 |

| **ChineseSubFinder + MovieRobot 等** | 组合方案 | 各司其职、可插拔 | 配置碎片化、工具间衔接差 | 一站式体验、统一配置管理 |

#### 11.2 easy-strm 的优势与风险

**核心优势（保持并强化）**：

1. **115 网盘深度整合**：市面上少有的"115 + TMDB + STRM + Emby"一站式方案，对中文用户有独特价值
2. **Web 化操作**：相比桌面应用，部署后即可远程操作，契合 NAS/Docker 使用场景
3. **任务化管理**：统一任务中心提供操作追溯和状态管理，比脚本方案更可靠
4. **单一工具覆盖全链路**：从识别到 STRM 不需要切换多个工具

**核心风险（需警惕）**：

1. **"什么都做但什么都不精"**：如果每个环节体验都只是"够用"，会被各环节的专业工具分流
2. **入门门槛与高级需求的矛盾**：简化入门可能牺牲效率派的可定制性，反之亦然
3. **115 API 依赖**：115 策略变动可能直接影响产品可用性

#### 12.3 长期战略方向（未来 2+ 季度）

| 编号 | 方向 | 理由 | 前置条件 |
| --- | --- | --- | --- |
| **S1** | **开放 API / Webhook** | 满足效率派的"可编程性"需求，同时为社区生态（第三方集成、移动端快捷操作）铺路 | 内部 API 稳定化、认证机制完善 |
| **S2** | **移动端适配或 PWA** | 用户在手机/平板上查看媒体整理状态的场景（在沙发上用手机看到下载完成，顺手触发整理） | 核心 Web 体验稳定，API 开放 |
| **S3** | **自动化策略引擎（IFTTT 风格）** | 让用户自定义"当 X 发生 → 自动执行 Y"规则，兼顾入门用户（模板）和高级用户（自定义规则） | Watch/Cron 功能稳定，用户反馈积极 |
| **S4** | **多语言国际化（英文优先）** | 媒体服务器用户群体天然国际化，英文支持可打开海外华人 + 全球通用市场 | 产品功能稳定，中文用户群稳固 |
