# 媒体库管理实施路线图

- 日期：2026-05-06
- 执行者：Codex
- 状态：实施计划
- 关联需求：[媒体库管理需求新增与重构](./MoviePilot参考需求新增与重构.md)

## 1. 实施目标

本路线图把“115 + 本地媒体库管理”需求拆成可实施阶段。第一轮不接入 PT、下载器、资源站和多网盘，优先建立媒体库管理的底座：

1. 同步索引：记录源文件、目标文件、STRM、元数据、媒体服务器路径之间的映射。
2. 同步任务：支持本地与 115 媒体源的全量同步、增量同步、差异对账。
3. 入库流水线：把识别、整理、STRM、元数据、媒体服务器刷新作为可追踪步骤。
4. 待处理独立页：承接识别失败、人工修正、重新入库。
5. 媒体库视图：展示条目健康度、STRM 状态、元数据完整度和最近任务。

## 2. 当前代码切入点

| 区域 | 现状 | 本轮处理方式 |
| --- | --- | --- |
| 媒体源 | `domain.MediaSource` 已有 `watch_path`、`auto_organize`、`organize_target_path`、`emby_library_id` | 保留现有字段，新增自动化规则字段，迁移时兼容映射 |
| 任务 | Redis 任务已有 `metadata`、进度、失败统计、取消/恢复 | 新增 `task_steps` 持久结构，Redis 继续作为运行态缓存 |
| 本地监控 | `WatchService` 已用 `fsnotify` 触发自动整理 | 改造为触发入库流水线，保留现有自动整理作为过渡 |
| 115 监控 | 当前通过轮询目录文件集合找新增 pickcode | 改为生活事件优先，定时差异对账兜底；第一步可先落差异对账 |
| STRM | 已有 `StrmConfig`、`StrmFile`、生成任务 | 扩展为同步/入库步骤，不立即删除独立配置页 |
| 前端 | Dashboard 子路由已存在文件管理、STRM、任务、115、整理规则 | 新增媒体库、待处理、同步任务页面，逐步重排菜单 |

### Phase 1：同步引擎 MVP

目标：让 115 与本地媒体源都能建立同步索引，并可手动触发全量/增量同步。

后端任务：

- 新增 `MediaSyncService`。
- 本地同步：
  - 扫描媒体源路径下的视频、字幕、NFO、图片文件。
  - 写入 `t_media_sync_index`。
  - 根据旧索引识别新增、修改、删除、移动或重命名。
- 115 同步：
  - 复用现有 115 文件列表能力。
  - 第一阶段先做目录文件树差异对账。
  - 生活事件接口作为后续增强点，接口设计先预留 `trigger_mode=life_event`。
- 新增 controller：
  - `POST /api/media/sources/:id/sync/full`
  - `POST /api/media/sources/:id/sync/incremental`
  - `GET /api/media/sources/:id/sync/index`
- 同步任务写入 `library_sync` 类型，步骤包括：scan_source、diff_index、write_index。

前端任务：

- 新增 `SyncTasks.vue` 页面。
- 媒体源列表增加“全量同步”“增量同步”“查看索引”操作。
- 新增 API 模块 `utils/api/sync.js`。

验收：

- 本地媒体源全量同步能写入索引。
- 115 媒体源全量同步能写入索引。
- 第二次同步能识别未变更并减少处理数量。
- 任务中心显示同步任务步骤。

### Phase 2：入库流水线与 STRM 联动

目标：把现有自动整理升级为可步骤化追踪的入库流水线。

后端任务：

- 新增 `LibraryPipelineService`。
- 新增任务类型 `library_pipeline`。
- 流水线默认步骤：
  1. identify
  2. organize
  3. strm
  4. metadata
  5. media_server_refresh
- 将 `WatchService.triggerAutoOrganize` 逐步改为触发 `LibraryPipelineService.Run`。
- 识别失败时写入 `t_pending_media_item`。
- STRM 步骤支持：
  - 默认跟随整理目标生成同构目录。
  - 允许媒体源自动化规则覆盖输出根目录和链接模板。
  - 成功后更新 `t_media_sync_index.strm_path`。
- Emby 步骤先支持现有 Emby 刷新，Jellyfin/Plex 只保留配置字段。

前端任务：

- 文件浏览器新增“按规则入库”按钮。
- 任务中心支持“从失败步骤重试”。
- STRM 配置页补充“作为自动化规则覆盖项”的说明和入口。

验收：

- 手动选择文件能发起入库流水线。
- 自动监控新增文件能发起入库流水线。
- STRM 步骤失败不会掩盖整理成功结果。
- 识别失败进入待处理清单。

### Phase 3：待处理独立页

目标：给识别失败和人工修正提供可操作入口。

后端任务：

- 新增 `PendingMediaController`：
  - `GET /api/media/pending`
  - `POST /api/media/pending/:id/identify`
  - `POST /api/media/pending/:id/run`
  - `POST /api/media/pending/:id/ignore`
- 待处理状态：
  - pending
  - identified
  - running
  - completed
  - ignored
  - failed
- 手动识别成功后写回识别缓存。

前端任务：

- 新增 `PendingMedia.vue` 独立页面。
- 菜单新增“待处理”。
- 支持筛选：未识别、已识别、失败、来源媒体源、媒体类型。
- 支持批量重新识别、批量重新入库、忽略。

验收：

- 识别失败项能在独立页面看到。
- 手动修正 TMDB 后可重新入库。
- 已忽略项不再出现在默认列表。

### Phase 4：媒体库视图与资产台账

目标：从“文件操作”升级到“媒体库健康管理”。

后端任务：

- 新增媒体库聚合查询。
- 基于 `t_media_sync_index` 输出 `MediaLibraryItem`。
- 支持筛选：
  - 未识别
  - 缺少 STRM
  - STRM 失效
  - 缺少 NFO
  - 缺少海报
  - 重复条目
- 增加单条详情：源文件、目标文件、STRM、元数据、媒体服务器信息、最近任务。

前端任务：

- 新增 `MediaLibrary.vue` 页面。
- 设计为高密度管理表格，不做营销式卡片首页。
- 单条详情使用抽屉或详情面板展示资产链路。
- 支持批量操作：重新识别、重新生成 STRM、刷新元数据、刷新媒体服务器、移入待处理。

验收：

- 用户可以不进入文件浏览器也能判断媒体库健康状态。
- 每个条目能追溯最近任务。

### Phase 5：自动化规则中心

目标：让用户按媒体源统一配置同步、入库、STRM、元数据和媒体服务器刷新策略。

后端任务：

- 扩展 `t_media_source` 或新增 `t_media_automation_rule`。
- 规则字段分组：
  - watch
  - sync
  - identify
  - organize
  - strm
  - metadata
  - media_server
- 提供规则预检接口，返回缺失配置和建议修复项。

前端任务：

- 新增 `AutomationRules.vue` 页面。
- 媒体源编辑弹窗保留基础字段，复杂规则转到规则页维护。
- 规则保存前展示预检结果。

验收：

- 本地与 115 媒体源使用同一套规则结构。
- 缺失关键配置时不会静默失败。

## 4. 推荐实施顺序

1. Phase 0：数据底座与任务步骤。
2. Phase 1：同步引擎 MVP。
3. Phase 3：待处理独立页骨架。
4. Phase 2：入库流水线与 STRM 联动。
5. Phase 4：媒体库视图与资产台账。
6. Phase 5：自动化规则中心。

说明：待处理页可在入库流水线完全接入前先做骨架，因为识别失败入口和任务中心关联会尽早用到。自动化规则中心放到后面，是为了避免在同步/流水线模型稳定前过早固化复杂表单。

## 7. 风险与约束

| 风险 | 处理 |
| --- | --- |
| 当前任务数据只存在 Redis，无法长期追溯 | 任务步骤进入 PostgreSQL，Redis 保留运行态 |
| 115 文件树扫描接口请求过多 | 默认 30 分钟差异对账，生活事件后续接入；前端提示低间隔风险 |
| 同步索引字段过早膨胀 | 第一阶段只存必要路径、标识和状态，复杂元数据后续扩展 |
| 自动整理旧链路与新流水线并存 | 先以流水线包裹旧服务，再逐步下沉步骤化 |
| 前端菜单一次性重排影响使用 | 先新增页面入口，后续再调整信息架构 |
