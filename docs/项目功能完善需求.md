## 1. 执行摘要

`easy-strm` 已经具备较完整的媒体整理产品面：本地与 115 媒体源、文件浏览、TMDB 识别、重命名与整理、刮削、STRM、Watch/Cron、任务中心、115 分享转存与云下载、Emby 管理与监控、通知及运维页面均已有实现。

当前主要问题不是“页面数量不足”，而是部分核心能力存在以下四类断点：

1. **数据操作边界不够可靠**：旧文件操作和刮削路径可越过媒体源根目录；空候选可能扩大为整目录整理；STRM 全量生成会清空输出目录的全部内容。
2. **任务状态与真实执行不一致**：取消后可能被覆盖为 completed，通用“恢复”只改 pending 而不重启执行器，Redis 任务 24 小时后自然消失。
3. **新装与运行态不一致**：fresh DB 缺少分享转存日志表，Cron 修改不热更新，Docker 没有媒体输入/STRM 输出挂载，默认镜像名会展开为无效的 `/easy-strm:latest`，默认登录说明和 Redis 健康检查也存在错误。
4. **已暴露能力与实际能力不一致**：STRM 增量接口固定 501，115 Open API 登录是占位，115 云刮削明确跳过，部分 STRM 配置字段可保存但未被执行链消费。

因此，建议暂停扩展 PT、资源搜索、订阅、下载器和插件市场等新产品面，先完成以下五个 P0 需求包：

| 顺序 | P0 需求包 | 解决的问题 |
| --- | --- | --- |
| 1 | RQ-01 文件操作边界与整理范围保护 | 防止越界操作、空选择扩大和根目录误操作 |
| 2 | RQ-02 STRM 安全生成与真实增量链路 | 防止误删非 STRM 文件、半成品覆盖和假完成 |
| 3 | RQ-03 版本化数据库迁移与 fresh-install 一致性 | 修复新装缺表、分享日志不可写和升级不可控 |
| 4 | RQ-04 Cron 运行态一致性 | 修复“接口成功但当前进程不生效” |
| 5 | RQ-05 Docker 新装、路径映射与首登契约 | 让容器新装可以实际处理媒体并可靠启动 |

## 6. 跨模块统一契约

### 6.1 任务状态机

任务主记录以 PostgreSQL 为准，Redis 只承载活跃进度、取消信号和短期缓存。所有任务类型使用同一状态语义：

```text
pending -> running -> completed | partial_success | failed | cancelled | skipped
                   -> interrupted -> pending/running（显式 resume）
                   -> tracking_timeout/unknown -> running/终态（显式 reconcile）
```

状态分组：

- 活跃态：`pending`、`running`。
- 待处理态：`interrupted`、`tracking_timeout`、`unknown`。它们不是终态，必须声明 `resumable` 或 `reconcilable`，且只能由对应 handler 通过条件更新推进。
- 终态：`completed`、`partial_success`、`failed`、`cancelled`、`skipped`。终态记录不可改写；失败项重试创建关联的新 attempt/子任务，保留原任务审计结果。

约束：

- 终态不可被普通更新覆盖；待处理态也不能被晚到 worker 直接改成 completed，所有推进都使用条件更新或版本号保证并发安全。
- `completed` 表示全部承诺动作成功，不得用于“仍在外部下载”“全部 skipped”或“部分文件失败”。
- `skipped` 仅表示已创建任务中的全部项目经规则判断无需处理；已知能力不可用时应在提交前返回 capability 错误，不创建伪任务。
- `resume/retry/reconcile` 必须真正调用对应 handler；没有实现的动作返回 409，并说明不支持原因。
- 任务响应必须声明 `cancellable`、`retryable`、`resumable`、`reconcilable` 和可用后处理动作。
- 任务详情包含阶段、成功/失败/跳过数量、逐项失败原因、创建/开始/完成时间和关联配置 ID。

### 6.2 HTTP 响应与分页

统一成功响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "request_id": "..."
}
```

统一失败响应：

```json
{
  "code": "FILE_OUT_OF_SCOPE",
  "message": "目标路径超出媒体源根目录",
  "details": {},
  "request_id": "..."
}
```

列表的 `data` 固定为：

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 50
}
```

前端请求层只解包一层 `data`，页面不得继续编写多层 fallback。

### 6.3 外部能力状态

115、TMDB、Emby、通知和本地挂载统一返回：

```json
{
  "capability": "cloud115_open_login",
  "status": "available|degraded|unavailable|not_configured",
  "reason_code": "DEVELOPER_ACCOUNT_PENDING",
  "message": "115 开放平台账号尚未配置",
  "checked_at": "2026-08-31T00:00:00+08:00"
}
```

UI 必须由能力状态决定显示、禁用或降级，不再通过点击后返回 500/501 才告知不可用。

## 7. 详细需求

### RQ-01 文件操作边界与整理范围保护

- 优先级：P0
- 类型：已证实缺陷
- 依赖：无；应最先实施

**目标**

所有本地读写、移动、复制、删除、重命名、刮削和链接操作只能发生在明确媒体源根目录内；“选择为空”不得被隐式解释为“全部”。

**需求范围**

1. 抽出并复用唯一 canonical path resolver，替换旧 `FileOperationService`、刮削、统一文件管理和整理执行中的平行路径拼接。
2. resolver 必须处理 `..`、绝对路径、Windows 不同盘符、大小写、空路径、`.`、符号链接、junction/reparse point 和目标尚不存在的父目录。
3. 删除/移动/写侧车文件时禁止操作媒体源根目录本身；源和目标都要在各自授权根内。
4. 整理执行接口在 `file_ids` 为空时返回 400 `EMPTY_SELECTION`；整目录整理改为独立显式动作，提交 `scope=directory`、目录、预计文件数并二次确认。
5. 前端候选数为 0 时禁用执行，展示“当前范围没有可整理视频”，不得发送空数组。
6. 旧重复接口在调用方迁移后删除，统一进入 Service 层的存储策略，不保留第二套边界规则。

**验收标准**

- `../x`、绝对路径、不同盘符、空路径、`.`、根目录、symlink/junction 逃逸全部被拒绝，且没有任何目标外文件变化。
- 合法嵌套路径的本地复制、移动、删除、重命名、硬链接、软链接和刮削全部通过回归。
- 空候选、空 `file_ids`、候选被刷新为 0 三种场景均不会启动整理任务。
- 显式整目录模式展示范围与数量，确认后才创建任务；取消不产生任务。

### RQ-02 STRM 安全生成、真实增量与配置语义

- 优先级：P0（安全全量与终态）；P1（增量和扩展字段）
- 类型：已证实缺陷 + 未完成能力
- 依赖：RQ-01；P0 取消终态先在本需求内交付最小条件更新，统一任务持久化与恢复依赖 RQ-06

**目标**

STRM 生成只管理本配置创建的文件，失败或取消时保留上一版可用结果；手动增量、Cron 增量和全量复用同一执行器。

**接口契约**

- `POST /strm/config/:id/preflight`：输入 `mode=incremental|full`，返回新增、更新、删除、未管理文件数、路径/权限检查和警告。
- `POST /strm/config/:id/generate/incremental`：返回 HTTP 202 和真实 `task_id/config_id/mode`。
- `POST /strm/config/:id/generate/full`：返回 HTTP 202；必须携带成功 preflight 的版本或重新执行 preflight。
- 同一配置同一时间只允许一个生成任务；第二个请求返回 409 和正在运行的任务 ID。

**执行要求**

1. 使用数据库 manifest（可复用 `t_strm_file`）或 ownership marker 记录受管文件，只删除本配置上次生成且本次已不存在的路径。
2. 混合目录中的 NFO、图片、字幕、用户目录和其他非受管文件必须保留；无法确认归属时拒绝清理。
3. 新文件先写 staging 并校验内容，完成后逐文件原子替换；扫描、生成或校验失败时旧 manifest 和旧文件仍可用。
4. 取消使用统一 context/sentinel 语义传播，最终状态保持 cancelled；部分文件失败为 partial_success 并返回逐项明细。
5. 页面默认主操作改为“增量生成”，全量保留高影响确认和影响预览。
6. `sync_mode/source_account/target_account/target_directory/auto_cleanup/cleanup_threshold/cleanup_policy/max_concurrency` 逐字段定义行为并接入执行；本期不支持的字段从 API、表单和模型删除，不允许继续“可保存但不生效”。
7. 手动、Cron、整理后触发三种入口使用同一 Service/Command，不再依赖 main 包回调桥的不同终态逻辑。

**验收标准**

- 目标目录预放任意未受管文件和子目录，全量/增量/取消/失败后均保持原样。
- 生成中断后旧 STRM 可继续使用；恢复或重跑不产生重复、残留 staging 或错误 manifest。
- HTTP 增量、Cron 增量对同一输入得到相同增删跳过结果。
- 生成 10 个、2 个失败时状态为 partial_success，结果显示成功 8、失败 2，而不是“成功生成 10”。
- 每个保留的扩展字段都有可观察行为测试；无测试的字段不得出现在发布版配置页。

### RQ-03 版本化数据库迁移与 fresh-install 一致性

- 优先级：P0
- 类型：已证实缺陷
- 依赖：无

**目标**

任何受支持版本都能通过同一迁移链得到一致 schema；迁移失败时应用拒绝就绪且以非零状态退出。

**需求范围**

1. 引入主流 Go/PostgreSQL 迁移器，建立 `schema_migrations`，迁移文件成为唯一 schema 来源；逐步移除 `db.go` 中千行启动 DDL 和破坏性即时 ALTER。
2. 将所有仍在使用的表纳入顺序迁移，首先补齐 `t_share_transfer_log`。
3. 修复分享日志批量写入：INSERT 省略 `create_time` 或使用 `CURRENT_TIMESTAMP`/有效时间；填齐 `cloud115_id`、目标目录和 SHA1。
4. 分享日志写入是转存提交契约的一部分。无法建立可重试审计记录时任务必须失败或回滚，不得只打印日志后继续报告成功。
5. 建唯一索引前先检测并处理历史重复 Cron 数据，输出明确冲突报告和保留规则。
6. 每个迁移在事务中执行；不支持事务的语句要单独标识、可重入并有失败恢复步骤。

**验收标准**

- 空 PostgreSQL 执行一次启动后，全部在用 DAO 都能完成最小 CRUD。
- 从每个已发布 schema 版本逐级升级到最新版本，最终结构与 fresh DB 一致。
- fresh DB 完成“密码分享解析→提交→日志更新→失败项重试”集成测试。
- 人为制造无效迁移时应用非零退出，readiness 为失败，旧 schema 数据不被部分修改。
- 重复 Cron 历史数据迁移前可报告，按规则处理后唯一索引成功创建。

### RQ-04 Cron 运行态一致性与任务身份

- 优先级：P0
- 类型：已证实缺陷
- 依赖：RQ-03；P0 scheduler 热更新可独立落地，统一执行器、任务身份和重启对账依赖 RQ-02/RQ-06

**目标**

Cron 的数据库状态、当前进程 scheduler、前端展示和实际触发时间始终一致，无需重启生效。

**需求范围**

1. 统一 main `CronTask` 与 domain `CronTask`，或提供唯一 adapter；向 `CronService` 和 `StrmService` 正确注入 scheduler。
2. 新增、修改表达式、启停、删除必须同步更新 scheduler。任一步失败需回滚，或记录 `runtime_sync_failed` 并返回失败，不能静默成功。
3. Cron 身份统一为 `(strm_config_id, task_type)`；同一 115 账号可为多个 STRM 配置创建独立任务。
4. “立即执行”先创建真实执行任务，再异步运行，并返回该执行任务 ID；Cron 配置 ID 单独返回。
5. API 返回数据库表达式、运行态是否已注册、真实 next run、最近执行任务 ID 和最近结果。
6. 识别缓存“凌晨 3 点清理”迁入统一 scheduler，按配置时区计算，不使用进程启动 24 小时后的 ticker。

**验收标准**

- 不重启服务即可新增、改表达式、停用、启用和删除任务；5 秒内运行态和 API 一致。
- scheduler 注入失败或表达式无效时数据库不保留伪成功配置。
- 同账号两个 STRM 配置可分别调度，删除一个不影响另一个。
- 立即执行响应中的任务 ID可直接在任务中心查询、取消并查看终态。
- 时区、夏令时边界和服务重启后的 next run 有自动化测试。

### RQ-06 可靠任务中心、真实恢复与后处理闭环

- 优先级：P1
- 类型：已证实缺陷
- 依赖：RQ-03

**目标**

任务中心成为长操作的可信来源：刷新页面、服务重启或外部超时后仍能说明真实状态，并只展示实际可用的动作。

**需求范围**

1. PostgreSQL 保存任务主记录、输入命令引用、checkpoint、结果摘要和逐项结果；Redis 只保存运行态进度和取消信号。
2. 建立 task type handler registry，每种任务声明 `execute/cancel/retry/resume/reconcile` 能力；前端由能力字段显示按钮。
3. 启动时将遗留 running 任务置为 interrupted，再由 handler 恢复、重试或对账；无法确认外部状态的任务置 unknown，不继续显示 running。
4. 终态使用条件更新，cancelled/failed/partial_success/completed 不可被晚到 goroutine 覆盖。
5. 历史支持服务端分页、关键词、类型、状态、日期范围和配置化保留；清理任务记录时同步清理 Redis 索引，不留下垃圾 ID。
6. 异步整理终态必须能打开结果详情，执行失败项重试、Emby 刷新和 STRM 生成；不再依赖不可达的同步结果弹窗。
7. 页面提交长任务后立即恢复可操作，提供“查看任务”“取消”“继续后台运行”；前端关闭或刷新后从任务中心恢复追踪。
8. 整理任务的恢复身份至少包含 source、path 和规范化 file IDs 指纹，不得只按 source ID 返回首个任务；active、interrupted 和可恢复任务必须分开。
9. Task DAO 全部使用构造注入的 Redis client，删除包级全局访问；任务索引使用集合/有序集合或 SCAN，不在请求链使用 Redis KEYS。

**验收标准**

- 对所有任务类型执行取消竞态测试，最终终态与实际执行一致且不可逆。
- 重启运行中的 STRM、整理、文件传输、分享转存、云下载任务后，状态变为可解释的 interrupted/恢复后状态。
- 不支持恢复的任务调用 `/resume` 返回 409；支持的任务会真正重新入队并推进进度。
- 30 天历史分页、Dashboard 7/30 日统计不依赖 24 小时 Redis TTL。
- 异步整理完成后可以从任务详情执行失败项重试、Emby 刷新和 STRM，动作结果产生关联子任务。
- 同一媒体源的两组不同目录/文件任务不会串用 checkpoint；并行 DAO 测试使用不同 Redis 实例时互不污染。

### RQ-07 安全、可扩展的统一文件管理

- 优先级：P1
- 类型：已证实缺陷 + 功能未完善
- 依赖：RQ-01、RQ-06

**目标**

统一文件管理在本地与 115 间处理大目录时不静默覆盖、不锁死页面，并给出逐项结果。

**需求范围**

1. `FileManagerTransferRequest` 增加 `conflict_policy=skip|overwrite|suffix`，默认 skip；新增 preflight 返回冲突文件、预计数量/大小和不支持项。
2. 复用现有 `ConflictPreviewModal` 展示源→目标、冲突策略和策略后的真实目标名。

7. 页面提交任务后不再等待最多 300 秒并锁住双栏；允许继续浏览并跳转任务详情。

**验收标准**

- 目标存在同名文件时默认保留目标；skip/overwrite/suffix 的 preflight 与实际结果一致。
- 在复制中断、磁盘满、网络失败场景下，不存在被截断的最终文件或遗留临时文件。
- 10 万项模拟 115 目录的首屏只请求一页，切页/搜索不预拉全部数据。
- 批量删除中第二项失败时，任务详情准确显示第一项成功、第二项失败及剩余项状态。
- 文件传输运行时双栏仍可浏览，刷新页面后可从任务中心继续追踪。

### RQ-11 文件搜索、识别与整理决策可解释

- 优先级：P1（契约修复）；P2/P3（体验增强）
- 类型：已证实缺陷 + 待验证产品建议
- 依赖：RQ-01、RQ-06、RQ-13

**目标**

搜索、识别、分类和整理的范围与决策对用户可见，减少误选和重复修正。

**需求范围**

1. 文件浏览统一 `keyword/type/page/page_size` 契约，搜索和 identified/unidentified/视频/目录筛选全部在服务端完整结果集上执行；切换筛选立即刷新。
2. 异步整理终态回流任务详情，展示原路径→目标路径、策略、成功/失败/跳过和后处理动作。
3. TMDB 候选增加 `match_score`、`match_level`、`match_reasons` 和 `requires_review`。评分基于标准化标题、年份、媒体类型、季集解析等可解释规则，不把 TMDB 投票分当匹配置信度。
4. 低置信度项集中筛选和批量复核；手动选择回写缓存并保留“人工修正”来源。
5. 分类策略增加样例文件/TMDB ID 试算，返回命中规则、每条条件、最终目录和未命中原因；检测同优先级重叠和每媒体类型多个 default。
6. 文件名识别和分类规则编辑增加 dirty 状态、离开确认和保存失败草稿保留。

**验收标准**

- 中文、空关键词、视频/目录筛选和跨页搜索结果由后端稳定分页，前后端参数一致。
- 任务完成后无需回到原弹窗即可查看整理结果并触发后处理。
- 固定回归样本集给出稳定 score/reason；低阈值项目默认进入待确认，不自动执行破坏性整理。
- 分类试算结果与真实整理目标一致；多个 default 或不可解释同分在保存时被拒绝或要求显式排序。

### RQ-12 首次使用与自动化配置向导

- 优先级：P1/P2
- 类型：待真实用户验证的产品增强
- 依赖：RQ-05、RQ-10、RQ-11、RQ-15

**目标**

降低“部署成功但不知道下一步做什么”的首次使用成本，同时保留高级配置入口。

**需求范围**

1. 首次登录展示本地状态诊断：数据库/Redis、媒体挂载、115、TMDB、STRM 输出、Emby；每项提供修复动作。
2. 媒体源分步创建：类型→账号/路径→读写/连接测试→整理模板→Watch；本地与 115 表单只显示相关字段。
3. STRM 四步向导：概念说明→选择 115 目录→容器路径映射与样例预览→生成测试；展示样例 `.strm` 内容和可访问性结果。
4. Watch 提供“仅监控”“标准自动整理”“整理+STRM+Emby”预设，高级参数可展开修改。
5. 任务完成在前端展示成功/失败/跳过摘要，并给出“看详情”“重试失败项”“生成 STRM”“刷新/打开 Emby”等实际可用动作。
6. 不引入新的外部埋点服务作为前置；先用本地匿名计数或可用性测试验证向导价值。

**验收标准**

- 新装测试用户可从首登完成一个媒体源创建、样例识别和 STRM 测试，不需要阅读源码或猜测容器路径。
- 每个向导步骤可返回修改，取消不保存半成品；高级用户可跳过向导进入原表单。
- 真实用户基线建立前，文档中的完成率/SUS/NPS 只标“待验证”，不得引用模拟值宣称提升。

### RQ-13 统一 API、账号能力与凭据操作契约

- 优先级：P1
- 类型：技术契约未完善
- 依赖：RQ-03

**目标**

前端、外部 API 和 MCP 使用同一稳定契约；用户相关动作由后端能力决定。

**需求范围**

1. 所有业务 Controller 使用第 6.2 节统一响应、错误码和分页；同一发布中同步迁移前端，不保留页面级多层兼容。
2. 建立 OpenAPI 契约或等价可生成规范，至少覆盖任务、媒体、STRM、Cron、文件管理、资源转存和云下载。
3. 前端登录后调用用户信息/能力接口，菜单和路由由 `role/capabilities` 驱动；不再依赖 `localStorage.user_name === admin`。
4. 补齐当前用户修改密码与 logout。改密验证旧密码，成功后明确当前会话处理策略；请求体不得指定任意用户名修改他人密码。
5. 全局 API Key 增加“生成/轮换”按钮、二次确认、仅一次明文展示和复制；关闭后明确不可恢复。保存配置时不再静默生成用户拿不到的 Key。
6. 统一请求层的错误提示责任：全局错误与页面业务错误不能重复 toast，支持 request ID 定位。
7. 日志禁止输出 JWT secret、Token、明文密码或密码摘要；密码从 MD5 迁移到主流自适应哈希，并在用户下次成功登录时平滑升级；统一使用一个 JWT 主版本。

**验收标准**

- 契约测试覆盖参数错误、成功和关键失败分支；前端源码不再出现 `data?.data?.data`。
- 非管理员直接访问管理员路由时，前端不显示入口且后端仍返回一致的权限错误。
- API Key 生成后只展示一次，复制可用；刷新页面后只能看到脱敏状态，轮换使旧 Key 失效。
- 修改密码和 logout 有前后端功能测试，错误旧密码不会修改数据。
- 认证失败/成功日志仅保留用户 ID、请求 ID 和结果，不包含任何可复用凭据；旧 MD5 账号登录迁移后仍可正常使用。

### RQ-14 前端长任务、Dashboard 与 Emby 健壮性

- 优先级：P2
- 类型：已证实质量缺口
- 依赖：RQ-06、RQ-13、RQ-15

**目标**

所有长任务和状态页面使用可取消、不会重叠、错误可见的统一请求机制。

**需求范围**

1. 抽取统一 task polling composable：串行请求、AbortController、session generation、指数退避、错误预算、终态停止和卸载清理。
2. 迁移 STRM、115 扫码/转存、FileManager、Emby 封面/Monitor 和日志自动刷新；禁止 async `setInterval` 产生重叠请求。
3. Dashboard 各模块独立 loading/error/retry，趋势按 date 做 outer join；侧栏健康状态来自真实 API，不显示硬编码“服务正常”。
4. Emby server/user/library 表单增加校验；封面任务识别所有终态和总超时，关闭弹窗停止轮询。
5. Nginx 上传上限与后端 10 MiB 契约一致，预留 multipart 余量；后端按实际读取字节判断上限，返回友好 413。
6. Emby Monitor 的筛选请求使用代次校验，旧响应不得覆盖新 server/filter；用户选项来自稳定数据源。
7. P3 可访问性：图标按钮补 aria-label，面包屑使用按钮/链接语义，覆盖键盘、焦点、Escape 和窄屏主流程。
8. 仅围绕稳定职责拆分超大页面的 composable/领域组件，统一轮询和错误归一化；ECharts 等重依赖按页面能力延迟加载，不为拆文件新增第二套状态或 API 体系。

**验收标准**

- 慢请求时间大于刷新间隔时，每个模块仍只有一个在途请求；切换页面/账号后旧响应被忽略。
- 任一 Dashboard 模块失败不影响其他模块展示，趋势缺日/乱序仍按日期正确对齐。
- Docker 下 0.9 MiB、1 MiB、10 MiB 图片按契约通过，超过 10 MiB 返回 413 且文案一致。
- completed 但无封面预览、网络连续失败、关闭弹窗三种场景均不会无限轮询。

### RQ-15 应用健康、生命周期、备份恢复与可观测性

- 优先级：P1/P2
- 类型：运维能力缺失
- 依赖：RQ-03、RQ-06

**目标**

部署系统能判断“进程活着”“核心依赖已就绪”“外部功能降级”，并能在升级或停机时保护任务与数据。

**需求范围**

1. 提供 `/health/live` 和 `/health/ready`：liveness 只判断进程事件循环；readiness 检查迁移、PostgreSQL、Redis 和必需目录；外部 115/TMDB/Emby 放 capability 状态，不拖垮 liveness。
2. 使用 `http.Server` 和根 context 处理信号，依次停止接收请求、Cron、Watch、通知、Emby collector 和队列 worker；运行中任务写 interrupted；关闭 DB/Redis。
3. 配置端口、读写超时、优雅停机时限和数据库连接池；启动/监听错误必须非零退出。
4. 提供版本化升级、升级前 PostgreSQL 备份、恢复和回滚文档；本地演练定义 RPO/RTO 并记录结果。
5. 日志增加 request/task/config ID，保留策略失败时回滚 UI；Dashboard days 限制为 1–365。
6. P2 增加本地可查看指标：任务吞吐/失败/时长、队列深度、外部 API 错误、Cron 漏触发、迁移版本和 goroutine 数；不把外部 SaaS 作为必需依赖。

**验收标准**

- DB、Redis、迁移、挂载分别故障时 readiness 给出明确原因，进程退出码与 Compose 状态正确。
- SIGTERM 后新请求停止，后台 worker 在时限内结束或把任务持久化为 interrupted，无无限 goroutine。
- 从备份恢复到空环境后可以登录、读取配置、查看任务历史和生成 STRM。
- `days=0/366/极大值` 返回 400，不产生大内存分配。

- 优先级：P1（关键回归）；P2（治理）

**需求范围**

2. 任务测试使用项目已有 miniredis，不因 localhost Redis 缺失跳过；fresh PostgreSQL 迁移和关键 API 使用本地临时数据库。
3. 23 个 E2E 分为：纯 mock、隔离本地写入、真实外部写入三组。默认门禁只运行前两组；真实外部组必须显式开关和测试账号。
4. P0/P1 必补回归：路径越界、空候选、STRM ownership、取消终态、Cron 热更新、fresh migration、密码分享、云下载重启、冲突策略和统一响应。
5. 以关键风险而非总覆盖率为门禁；阶段目标建议 Service 关键模块 ≥80%、关键 Controller ≥60%，同时禁止关键测试 skip。
6. 发布使用语义版本、变更日志、镜像 digest、迁移兼容矩阵和回滚说明。
7. 文档标记 `current/as-built`、`planned`、`superseded`、`archived`。更新 README 和产品页面清单，修正 Login 的“资产台账”旧文案；将旧 PT/追剧/qBittorrent/PostHog 路线图标为 superseded，不重新当作缺失功能。

**验收标准**

- 发布镜像可对应到源码版本和 schema 版本，升级/回滚矩阵可执行。
- README、页面路由、API/能力清单和产品边界一致；全文不再包含个人绝对路径或把历史规划写成当前承诺。

## 12. 主要风险与决策点

| 风险 | 影响 | 处理原则 |
| --- | --- | --- |
| 从 Redis 任务迁到 PG | 历史短期任务可能缺少完整 command/checkpoint | 只迁移可恢复字段；未知状态明确标记，不伪造恢复 |
| STRM ownership 上线前已有混合目录 | 无法可靠判断历史文件归属 | 首次 preflight 只导入可由 DB 记录确认的文件；其余视为未管理并保留 |
| 统一 API 是破坏性变更 | 前后端需同版本发布 | 先生成契约测试，同一发布同步迁移全部 SPA 调用方 |
| 115 外部 API 行为变化 | live E2E 难稳定 | driver 适配层 mock + 明确标记的外部测试账号，不把 live 写入放入默认门禁 |
| Windows/Linux 路径语义不同 | junction、盘符、硬链接行为不同 | 分平台 resolver 测试；Docker 主支持路径单独验证 |
| 版本化迁移接管 `db.go` | 现有历史 schema 可能不一致 | 先做只读 schema audit 和基线迁移，再逐段删除启动 DDL |
| 首次向导价值未验证 | 可能增加维护面 | 复用现有表单和 capability，不创建第二套业务规则；真实测试后再扩展 |
