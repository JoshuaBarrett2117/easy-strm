## 一、背景与现状判断

基于当前仓库文档与代码状态，Easy-STRM 已经从最初的 115 直链与 STRM 生成工具，逐步扩展到媒体库管理、TMDB 识别、更名、自动整理、115 秒传与跨源处理方向。

当前已有基础包括：

- 基础核心：115 账号管理、直链解析、STRM 全量/增量生成、定时任务、任务查看。
- MediaManager：媒体源管理、本地/115 文件浏览、文件操作、TMDB 识别、重命名、整理入口。
- MediaOrganize：整理预览、整理执行、分类规则、冲突策略、115 整理能力已开始接入。
- 传输能力：后端已出现 SHA1、BloomFilter、InstantTransfer、TransferScheduler 等相关服务文件。
- 前端入口：`MediaManager.vue` 已承载媒体源、文件浏览、TMDB、重命名、整理弹窗等交互。

现阶段最关键的问题不是“继续扩新模块”，而是“把已铺开的能力收敛成稳定可用的闭环”。因此后续迭代建议围绕 `MediaManager Beta -> 自动化增强 -> STRM 深度整合 -> 媒体服务器联动` 逐步推进。

## 二、推荐迭代主线

### 主线 A：MediaManager Beta 可用化

目标是让用户可以在同一个页面完成：

1. 选择媒体源。
2. 浏览本地或 115 文件。
3. 识别 TMDB。
4. 预览重命名与整理路径。
5. 执行重命名、复制、移动或整理。
6. 查看成功、失败、跳过的结果摘要。

建议优先级：P0。

原因：

- 现有代码与文档已经围绕 MediaManager 展开，继续打磨闭环成本最低。
- 该能力最容易形成用户可感知价值。
- 它会成为后续 STRM、自动整理、媒体服务器刷新的上游基础。

### 主线 B：批量任务与反馈统一

目标是把批量识别、批量重命名、批量整理、跨源复制等长操作统一成可追踪任务。

建议优先级：P0-P1。

关键要求：

- 所有批量操作都返回统一摘要：总数、成功数、失败数、跳过数。
- 失败项需要展示文件名、失败原因、建议处理方式。
- 页面上区分执行中、完成、部分失败、失败四类状态。
- 任务完成后支持刷新当前目录或进入任务详情。

### 主线 C：115 与本地能力边界对齐

目标是避免前端出现入口，但后端能力不完整或行为不一致。

建议优先级：P1。

关键要求：

- 明确本地源与 115 源分别支持哪些操作。
- 本地源优先保证整理闭环稳定。
- 115 源优先保证浏览、识别、重命名、复制/移动基础操作稳定。
- 不支持的行为必须明确提示，而不是静默失败。

### 主线 D：STRM 与整理结果联动

目标是让 MediaManager 整理后的目录可以直接触发 STRM 生成或刷新。

建议优先级：P1-P2。

建议方向：

- 在整理完成结果页提供“生成 STRM”入口。
- STRM 配置中可选择 MediaManager 媒体源。
- 整理任务完成后，可选择自动触发增量 STRM。
- 任务列表中统一展示整理任务与 STRM 任务关联关系。

### 主线 E：媒体服务器联动

目标是整理完成后自动刷新 Jellyfin/Emby 媒体库。

建议优先级：P2。

建议先做 Jellyfin/Emby，Plex 可放到后续讨论：

- 设置页配置媒体服务器地址、Token、媒体库 ID。
- 整理成功后触发指定媒体库刷新。
- 任务结果中记录刷新成功或失败。
- 首期只支持手动触发和整理后触发，不做复杂策略。

## 三、版本切片建议

| 版本 | 主题 | 主要交付 | 优先级 |
| :--- | :--- | :--- | :--- |
| Beta 1 | MediaManager 可用化 | 本地整理闭环、TMDB Top3、重命名预览执行、结果摘要 | P0 |
| Beta 2 | 批量任务统一 | 批量识别/重命名/整理结果面板、失败明细、任务状态统一 | P0 |

## 四、需求讨论问题

这些问题建议在下一轮需求讨论中确认，确认后即可拆成开发任务。

### 4.1 MediaManager Beta 的完成边界

建议默认口径：

- 本地媒体源完整支持识别、重命名、整理。
- 115 媒体源支持浏览、识别、基础重命名，整理能力先标注为增强能力。
- 批量操作必须有结果摘要。

待确认：

- Beta 1 是否必须包含 115 整理执行，还是先确保本地整理闭环？ 
-- 包含115整理执行
- 批量整理是否需要异步任务化，还是 Beta 1 可以先同步返回结果？
-- 需要异步任务化
- TMDB 候选结果是否默认展示 Top 3，并允许用户手动选择？
-- 是

### 4.2 整理与冲突策略

建议默认口径：

- 整理执行前必须先预览。
- 默认冲突策略为跳过。
- 允许用户在执行前选择覆盖或追加序号。

待确认：

- 覆盖操作是否需要二次确认？
-- 不需要
- `move` 与 `copy` 的默认值选哪个？建议默认 `copy`。
-- 默认move
- 失败项是否需要支持一键重试？
-- 需要支持

### 4.3 115 源的迭代边界

建议默认口径：

- 115 源优先解决目录导航、字段一致性、失败提示。
- 115 大批量整理应进入任务体系，不在页面同步等待。
- 115 操作加入节流，沿用已有 200ms 间隔和调度器思路。

待确认：

- 115 整理时，目标路径不存在是否自动创建？
-- 需要自动创建
- 115 重命名后再移动，还是先移动再重命名？
-- 重命名后再移动
- 115 跨账号场景优先支持秒传，还是先支持同账号移动/复制？
-- 先支持同账号移动/复制
### 4.4 STRM 联动

建议默认口径：

- MediaManager 是上游整理工具，STRM 是下游生成工具。
- 整理完成后可手动触发 STRM。
- 自动触发 STRM 放到后续版本，避免 Beta 阶段链路过长。

待确认：

- 是否需要在 MediaManager 页面直接选择 STRM 配置？
-- 不需要
- 整理后的目标目录是否自动写入 STRM 配置？
-- 是
- STRM 增量生成是否要和整理任务合并显示？
-- 是
### 4.5 媒体服务器联动

建议默认口径：

- 首期支持 Jellyfin/Emby API 刷新。
- 刷新失败只记录结果，不阻塞整理任务成功状态。
- 媒体服务器配置放在设置页。

待确认：

- 首期是否需要 Plex？
-- 不需要，仅支持emby即可
- 刷新粒度是整个媒体库，还是按路径刷新？
-- 按路径刷新
- 是否允许每个媒体源绑定不同媒体库？
-- 允许
## 五、验收口径建议

### 5.1 Beta 1 验收

- 可创建本地媒体源并浏览目录。
- 可对单个视频文件执行 TMDB 识别并看到候选结果。
- 可对单个文件预览重命名并执行。
- 可选择多个文件生成整理预览。
- 可执行本地整理并看到成功、失败、跳过摘要。
- 冲突策略至少支持跳过与追加序号。

### 5.2 Beta 2 验收

- 批量识别、批量重命名、批量整理都具备统一结果面板。
- 失败项有中文可读原因。
- 批量任务不会阻塞页面基础浏览。
- 执行完成后可以刷新当前目录。

### 5.3 Beta 3 验收

- 115 源可稳定进入多级目录并返回。
- 115 源可执行支持范围内的基础操作。
- 不支持的 115 能力有明确提示。
- 本地源与 115 源返回字段尽量统一，前端分支减少。

## 六、建议优先处理的技术债

| 项目 | 建议 |
| :--- | :--- |
| API 命名 | 收敛 `/media/tmdb/*` 与 `/media/organize/*` 中重复的识别/更名接口，避免前端同时维护两套语义 |
| 任务结果 | 抽象统一的批量结果结构，避免每个接口单独返回 |
| 115 导航 | 补齐当前目录、返回上级、根目录返回、面包屑路径 |
| 文档编码 | 部分历史 Markdown 显示为乱码，建议后续统一 UTF-8 保存 |
| 测试数据 | 保留最小可复现的本地媒体目录和 115 mock 数据，支撑回归测试 |

## 七、下一步建议

建议下一轮需求讨论按以下顺序进行：

1. 先确认 Beta 1 是否只聚焦本地整理闭环。
2. 再确认 115 整理是否进入 Beta 3。
3. 然后确认批量任务是否必须异步化。
4. 最后确认 STRM 联动和媒体服务器联动的首期范围。

如果不做额外讨论，建议默认进入以下开发切片：

| 顺序 | 开发切片 | 目标 |
| :--- | :--- | :--- |
| 1 | 本地整理预览与执行闭环 | 让 Beta 1 有明确可用主流程 |
| 2 | 统一批量结果结构 | 让页面能稳定展示成功/失败/跳过 |
| 3 | TMDB 候选选择与手动绑定 | 提升识别准确性 |
| 4 | 115 导航与能力边界提示 | 降低云盘场景误操作和困惑 |
| 5 | 整理完成后触发 STRM | 打通媒体管理到 STRM 生成链路 |

## 八、结论

后续迭代建议以 `MediaManager Beta` 为核心，不再优先扩展新模块。第一目标是把“媒体源浏览 -> TMDB 识别 -> 重命名预览 -> 整理执行 -> 结果反馈”做成稳定闭环。等这个闭环稳定后，再逐步接入 115 深度整理、STRM 联动和 Jellyfin/Emby 刷新。
