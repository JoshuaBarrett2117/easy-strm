# Easy-STRM 下一步升级需求文档

> 文档版本：v1.0  
> 编写日期：2026-04-06  
> 编写者：Codex

## 一、升级背景

当前项目已经完成了 MediaManager 的基础骨架建设，包含以下已落地能力：

- 媒体源管理：支持本地目录与 115 媒体源配置
- 文件浏览：支持基础列表查看、分页、搜索、目录进入
- TMDB 能力：支持搜索、单文件识别、基础缓存
- 更名能力：支持单文件重命名、批量重命名预览与执行入口
- 文件操作：支持删除、移动、复制、批量操作接口骨架

但从当前代码状态看，MediaManager 仍处于“功能已铺开、闭环未打通”的阶段，距离稳定可用还有明显差距，主要体现在：

- 自动整理能力只完成了部分本地场景，115 场景尚未打通
- 整理执行流程与目标路径、移动/复制策略尚未形成完整闭环
- 前端页面以“源管理 + 文件浏览”为主，整理任务流尚未形成完整操作路径
- 批量识别、批量重命名、任务反馈、失败处理的一致性还不足
- 当前测试覆盖集中在少量 DAO/Service，缺少 TMDB、重命名、整理链路验证

因此，下一步升级建议不再扩散新模块，而是聚焦“MediaManager 可用化升级”，把已建设的能力做成可稳定交付的版本。

## 二、升级目标

### 2.1 目标版本

定义下一阶段版本为：`MediaManager Beta`

### 2.2 核心目标

1. 打通从“媒体源浏览”到“识别、重命名、整理执行、任务反馈”的完整闭环。
2. 先把本地媒体整理场景做实，形成可稳定使用的基础能力。
3. 补齐 115 场景下的浏览、识别、重命名、整理边界说明，避免前后端能力不一致。
4. 将批量操作纳入统一任务反馈体系，降低长任务的不确定性。
5. 用最少的新概念完成升级，优先复用现有页面、现有任务体系、现有数据结构。

## 三、本次升级范围

### 3.1 In Scope

- MediaManager 页面可用性补强
- 本地媒体整理闭环打通
- TMDB 识别与更名流程补全
- 批量任务反馈与结果展示
- 115 媒体源的浏览与操作体验修正
- 测试补齐与文档补齐

### 3.2 Out of Scope

- 全新独立模块拆分
- 复杂 Watch Folder 实时监听
- Emby/Jellyfin/Plex 联动刷新
- 高级回滚系统
- 播放日志、空间清理、通知中心
- 大规模架构重构

## 四、当前问题归纳

| 编号 | 问题 | 影响 |
| :--- | :--- | :--- |
| P1 | 自动整理仅部分支持本地文件，115 整理未落地 | 用户无法形成统一整理体验 |
| P2 | 整理执行对目标目录、移动/复制策略支持不完整 | 预览与执行结果可能不一致 |
| P3 | 前端批量重命名/TMDB/整理接口语义存在分散 | 页面能力难以稳定串联 |
| P4 | 115 浏览依赖 CID 导航，面包屑与返回体验较弱 | 深层目录操作成本高 |
| P5 | 批量任务缺少统一结果反馈与失败汇总 | 用户难判断执行结果 |
| P6 | 测试覆盖不足，升级风险高 | 容易出现回归问题 |

## 五、需求设计

### 5.1 需求一：MediaManager 操作闭环升级

#### 目标

让用户能够在一个页面内完成以下流程：

1. 选择媒体源
2. 浏览并筛选文件
3. 发起 TMDB 识别
4. 查看重命名预览
5. 执行重命名或整理
6. 查看执行结果与失败原因

#### 功能要求

- MediaManager 页面新增“整理”主操作入口
- 文件列表支持按“未识别 / 已识别 / 目录 / 视频文件”快速筛选
- 选中文件后，操作区需要明确区分：识别、重命名、整理、删除
- 批量操作执行后，页面必须展示成功数、失败数、跳过数
- 执行完成后支持一键刷新当前目录

#### 验收标准

- 用户在不跳转其他页面的情况下可完成一次完整批量整理流程
- 任何批量操作完成后，页面都能看到明确结果摘要
- 失败项必须展示可读原因，不能只返回通用报错

### 5.2 需求二：本地媒体整理闭环打通

#### 目标

优先将“本地媒体源 -> TMDB 识别 -> 重命名 -> 归档目录整理”做成 Beta 可用能力。

#### 功能要求

- 支持选择源目录、目标目录、媒体类型、命名模板
- 支持“仅预览”与“确认执行”两段式流程
- 执行时支持 `copy` 与 `move` 两种模式
- 支持冲突策略：`skip`、`overwrite`、`suffix`
- 预览结果必须展示：原文件名、识别结果、新文件名、目标路径、可能冲突
- 执行结果必须展示：成功、失败、跳过状态

#### 验收标准

- 至少支持电影、剧集两种媒体类型
- 本地场景下，预览结果与最终执行结果保持一致
- 冲突策略生效可验证
- 批量整理 100 个文件时，结果可查询且页面不阻塞

### 5.3 需求三：TMDB 识别体验补全

#### 目标

从“能调 API”升级为“可支撑日常整理”的识别能力。

#### 功能要求

- 单文件识别支持展示 Top 3 候选结果
- 批量识别支持跳过目录，只处理媒体文件
- 识别结果缓存保留现有 7 天策略
- 对无法识别的文件，允许用户手动搜索并绑定结果
- 识别结果写回文件列表，支持列表直接查看识别标题

#### 验收标准

- 常见命名格式可自动识别电影/剧集
- 批量识别失败不影响其他文件继续处理
- 手动绑定后再次打开列表可看到识别结果

### 5.4 需求四：重命名能力升级

#### 目标

让重命名从“能改名”升级为“可控、可预览、可批量”。

#### 功能要求

- 单文件重命名支持保留原扩展名
- 批量重命名必须先预览后执行
- 重命名模板继续复用现有预设机制
- 增加预设展示与选择能力
- 对剧集文件，模板变量至少支持 `{name}`、`{season}`、`{episode}`
- 对电影文件，模板变量至少支持 `{name}`、`{year}`

#### 验收标准

- 单文件与批量重命名规则一致
- 重命名后文件列表刷新可见
- 同名冲突场景可按策略处理

### 5.5 需求五：115 媒体源体验修正

#### 目标

保持 115 场景“可浏览、可识别、可基础操作”，但不在本期强行承诺完整整理闭环。

#### 功能要求

- 优化 115 目录导航体验，至少补齐“当前目录名 + 返回上级 + 根目录返回”
- 115 文件列表与本地文件列表字段尽量统一
- 支持 115 文件的识别、删除、基础重命名能力边界说明
- 如某能力当前不支持，页面必须给出明确提示，而不是静默失败

#### 验收标准

- 用户可稳定进入 115 多级目录并返回
- 115 不支持的整理行为有明确提示
- 前后端返回字段保持一致，减少页面适配分支

### 5.6 需求六：任务反馈与可观测性补齐

#### 目标

将批量操作纳入统一任务反馈机制，降低“点了按钮但不知道发生了什么”的体验问题。

#### 功能要求

- 批量识别、批量重命名、批量整理统一进入任务体系或统一结果面板
- 任务至少包含：任务类型、开始时间、结束时间、总数、成功数、失败数
- 支持查看失败项列表
- 支持任务完成后的结果摘要提示

#### 验收标准

- 任一批量任务都能看到可追踪结果
- 用户可区分“执行中”“已完成”“部分失败”三种状态

## 六、页面改动建议

### 6.1 MediaManager 页面

建议保留当前单页结构，不新增独立复杂页面，优先补齐以下区域：

- 媒体源列表区：保持现状
- 文件浏览区：增加状态筛选、批量操作栏
- 整理工作台：新增右侧抽屉或弹窗，承载整理参数、模板选择、预览结果
- 任务结果区：新增轻量结果面板或复用现有任务弹窗

### 6.2 交互原则

- 先预览，后执行
- 批量操作默认保守，不做静默覆盖
- 所有失败都要有中文提示
- 尽量复用现有 Element Plus 组件，避免额外设计成本

## 七、接口与数据要求

### 7.1 接口整理原则

- MediaManager 相关接口按“媒体源 / 文件操作 / TMDB / 重命名 / 整理 / 任务”六类收敛
- 前端接口命名与后端路由保持一致，减少适配层歧义
- 批量接口统一返回：总数、成功数、失败数、结果明细

### 7.2 返回结构统一建议

统一返回字段建议为：

- `success`
- `message`
- `data`
- `summary`
- `items`

其中：

- `summary` 用于批量统计
- `items` 用于失败明细或逐项结果

## 八、测试与验收要求

### 8.1 必测范围

- 媒体源 CRUD
- 本地文件列表浏览与目录切换
- TMDB 单文件识别与批量识别
- 单文件重命名与批量重命名
- 本地整理预览与执行
- 冲突策略处理
- 失败场景提示

### 8.2 建议补齐的测试类型

- Service 单元测试：`TmdbService`、`RenameService`、`OrganizeService`
- Controller 接口测试：媒体管理相关主链路
- 前端最小冒烟：MediaManager 页面基础流程

### 8.3 验收口径

满足以下条件即可视为本阶段完成：

1. 本地媒体整理流程可稳定跑通。
2. 批量识别、批量重命名、批量整理均有明确结果反馈。
3. 115 场景的能力边界清晰，不出现“UI 有入口但后端不支持”的误导。
4. 关键服务层具备最小可回归测试。

## 九、优先级与排期建议

| 阶段 | 内容 | 优先级 |
| :--- | :--- | :--- |
| Phase 1 | MediaManager 页面闭环补强、本地整理预览与执行打通 | P0 |
| Phase 1 | TMDB Top3 候选、批量识别结果回写 | P0 |
| Phase 2 | 批量重命名统一预览执行、冲突策略补齐 | P1 |
| Phase 2 | 任务反馈与结果面板补齐 | P1 |
| Phase 3 | 115 导航体验修正、字段一致性整理 | P1 |
| Phase 3 | 自动整理规则配置与预设管理 | P2 |

## 十、实施建议

### 10.1 建议开发顺序

1. 先修正前后端接口语义与页面入口一致性。
2. 再打通本地整理的预览与执行闭环。
3. 然后补齐批量识别、批量重命名、任务结果反馈。
4. 最后修正 115 场景体验与不支持能力提示。

### 10.2 建议版本定义

- `Beta 1`：本地整理闭环可用
- `Beta 2`：批量操作与任务反馈稳定
- `Beta 3`：115 浏览体验修正完成

## 十一、最终结论

下一步升级不建议继续横向扩需求，而应集中资源完成 `MediaManager Beta`。这条路线有三个优势：

- 基于现有代码骨架，改造成本最低
- 能最快形成用户可感知的完整能力闭环
- 能为后续 115 整理、媒体服务器联动、自动任务扩展打下稳定基础

如果进入开发执行阶段，建议直接以“本地整理闭环 + 批量反馈统一”作为第一批落地目标。
