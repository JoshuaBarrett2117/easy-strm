# Easy-STRM V3.0+ 产品演进规划

> 版本：v3.0-alpha | 撰写日期：2026-03-25 | 状态：规划中

***

## 一、核心演进方向

基于现有的 **115云账号管理** 中的「转存账号」和「转存目录」配置，构建跨账号 **SHA1 秒传同步** 能力。

**现有基础**：
- 每个 115 账号已配置 `transfer_account_id`（转存目标账号）和 `transfer_directory`（转存目录）
- 已有 `t_cloud_115` 表存储账号信息
- 已有 `t_strm_config` 表管理 STRM 生成配置

**演进目标**：
- 利用 115 的 SHA1 秒传 API，实现「资源号 → VIP观影号」的文件秒传同步
- 复用现有转存账号配置，无需额外建立复杂的文件夹映射

**一对多同步的实现**：
- 同一目标多配置：1个 cloud115 账号 → 1个 transfer_account_id目标 + N个 strm_config（不同目录）
- 多目标多账号：M个 cloud115 账号 → M个 transfer_account_id 目标
- 每个 strm_config 配置可以独立设置不同的 net_disk_path，实现精细化同步

### 2.2 SHA1 秒传同步服务

#### 秒传流程设计

```
┌─────────────────────────────────────────────────────────────────────┐
│                      秒传同步流程                                      │
│                                                                     │
│  [任务触发] ──▶ [文件SHA1计算] ──▶ [Redis布隆过滤器检查] ──▶ [Redis缓存查询]  │
│                                              │                       │
│                                              │ 存在                  │
│                                              ▼                       │
│                                        [跳过/已存在]                  │
│                                                                      │
│                                              │ 不存在                 │
│                                              ▼                       │
│                                  [115秒传API] ──▶ [成功?]            │
│                                                      │               │
│                                    ┌─────────────────┼───────────┐  │
│                                    │                 │           │  │
│                                  是 │                 │ 否         │  │
│                                    ▼                 ▼           │  │
│                            [STRM生成]      [回退直链解析+转存]      │  │
│                                    │                 │           │  │
│                                    └────────┬────────┘           │  │
│                                             │                    │  │
│                                             ▼                    │  │
│                                     [更新缓存+通知]                │  │
└─────────────────────────────────────────────────────────────────────┘
```

#### 核心组件

| 组件 | 职责 |
| :--- | :--- |
| HashService | 计算文件 SHA1，支持大文件分片计算 |
| BloomFilter | Redis布隆过滤器，快速判断文件是否可能已存在 |
| InstantTransferService | 调用 115 秒传 API，处理秒传成功/失败逻辑 |
| TransferScheduler | 同步调度器，处理限速、熔断、优先级队列 |

#### Hash 缓存策略

| 缓存层 | 存储内容 | TTL | 说明 |
| :--- | :--- | :--- | :--- |
| Redis布隆过滤器 | SHA1 集合 | 进程生命周期 | 零漏报，快速过滤 |
| Redis | SHA1 → 文件CID映射 | 7天 | 秒传命中记录 |

#### 风控机制

| 防护措施 | 说明 |
| :--- | :--- |
| 请求间隔 | 单账号秒传间隔 ≥ 200ms |
| 熔断器 | 连续失败 5 次，冷却 5 分钟 |
| 分布式限速 | 多账号轮询，单 IP 总 QPS ≤ 20 |
| 流量监控 | 触发阈值时自动降级为「直链模式」 |

## 三、方案可行性分析

### 3.1 技术难点

| 功能 | 难点 | 风险等级 |
| :--- | :--- | :--- |
| 秒传 API 调用 | 115 风控策略不透明 | ⚠️ 高 |
| 多账号并发调度 | 资源号 QPS 控制 | ⚠️ 中 |
| SHA1 计算 | 大文件分片计算性能 | ✅ 低 |
| 直链保活 | 需定时刷新 + 缓存 | ✅ 低 |

### 3.2 架构说明

复用现有 `t_cloud_115` 表结构，扩展字段：
- 新增 `account_type`, `quota_used`, `priority`, `status`, `cooling_start_time`

复用现有 `t_strm_config` 表结构，扩展字段：
- 新增 `sync_mode`, `source_account`, `target_account`, `target_directory`, `auto_cleanup`, `cleanup_threshold`, `cleanup_policy`, `max_concurrency`

新建表：
- `t_sync_task`：同步任务记录（可选，复用 Redis 任务队列亦可）
- `t_notification_config`：通知渠道配置
- `t_sha1_cache`：SHA1 → 文件CID 缓存（可选，Redis 亦可）
- `t_play_log`：播放日志记录（用于 oldest_unplayed 清理策略）

### 3.3 分阶段路线图

| 阶段 | 功能 | 优先级 |
| :--- | :--- | :--- |
| V3.1 | 账号管理增强（类型/状态/优先级）+ SHA1 计算服务 | P0 |

- Cookie / Token：前端加密存储，后端不落盘，接口返回时脱敏展示

## 五、需求澄清 (Q&A) - 已完成

### Q1: 秒传API集成
**Q**: 115网盘的秒传API具体是哪个endpoint？使用 driver 库已有的方法还是自行调用？秒传是否需要先计算文件SHA1？

**A**: 使用秒传接口，driver中可能有秒传接口的实现，你可以观察下相关代码。秒传需要先计算sha1，目前项目中似乎没有sha1计算的实现需要你创建

### Q2: 同步触发机制
**Q**: 「目录监控 (Watchfolder)」功能是否仍需保留？

**A**: 目前监控暂时先不做，忽略该需求

### Q3: 通知模块
**Q**: 通知渠道（Telegram/Server酱/Email）的配置是全局配置还是每个账号独立配置？通知触发条件有哪些？

**A**: 通知渠道为全局配置，通知触发条件暂时只有任务完成，后续有需要再加

### Q4: 账号「冷却」状态
**Q**: cooling 状态是如何触发的？账号被cooling后多久会自动恢复？

**A**: 由系统自动判断，但是允许手动操作为active状态

### Q5: 秒传与现有转存配置的关系
**Q**: transfer_account_id 是否直接作为秒传的目标配置？秒传成功后是否还需要执行「转存」操作？

**A**: 
1. 直接作为秒传的目标配置
2. 不需要额外映射关系
3. 不需要，秒传本身就包含了转存逻辑

### Q6: 同步任务配置层级
**Q**: 同步策略是在 t_strm_config 级别还是账号级别？一个资源号是否可以同步到多个VIP账号？

**A**:
1. 同步策略在主账号配置
2. 一个资源号可以同步到多个VIP账号（通过多个strm_config或多个cloud115子账号实现）

### Q7: 布隆过滤器实现
**Q**: 布隆过滤器的实现是在 Redis 中还是本地内存中？

**A**: 实现在Redis中

### Q8: 任务去重与取消
**Q**: 如果同一个文件被多次提交同步应该如何处理？同步任务是否可以取消？

**A**:
1. 跳过（已存在的文件不重复处理）
2. 可以取消，取消后部分同步文件忽略

### Q9: 空间清理策略
**Q**: 清理策略是针对源账号还是目标账号？「oldest_unplayed」是如何判断未播放的？

**A**:
1. 针对主账号
2. 需要播放日志记录
