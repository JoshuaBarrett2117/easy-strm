# 项目开发规范

- 日期：2026-04-18
- 维护者：Codex

## 1. 适用范围

本文档适用于 `easy-strm` 全项目的后端、前端、测试、联调与回归验证。

目标只有一个：把历史测试里反复踩过的坑，收敛成统一的开发约定，避免同类问题再次出现。

## 2. 基本原则

1. 先理解现有实现，再做改动。
2. 先修复缺陷，再扩展功能。
3. 小步修改，保持每次变更都可编译、可验证。
4. 新代码必须符合当前项目已有风格，不引入新的混乱约定。
5. 任何会影响测试结果的改动，都要同步检查测试代码和验证脚本。

## 3. 最容易出问题的地方

### 3.1 初始化顺序必须统一

- 数据库、Redis、DAO、Service、Controller、路由注册要按固定顺序初始化。
- 不要把全局依赖初始化散落在不同路由函数里。
- 这类问题的典型后果是页面某个接口直接返回 `500`，但根因其实是初始化时机不对。

### 3.2 测试签名变更必须同步修改

- 任何函数参数、返回值、结构体字段一旦改动，相关测试必须一起更新。
- 这次就出现过测试调用和真实函数签名不一致，导致 `go test ./...` 直接编译失败。
- 结论：代码改了不算完，测试编译通过才算完。

### 3.3 前后端响应结构必须统一

- 后端返回结构要稳定，前端不要到处兼容 `data.data`、`data.data.data` 这种嵌套写法。
- 如果历史接口已经分叉，优先在后端收敛，或者在前端做单一适配层，不要在页面里散写兼容逻辑。
- 新接口必须一次定型，避免后续页面继续叠兼容分支。

### 3.4 外部依赖失败要区分“异常”与“预期失败”

- TMDB、Emby、115、邮件、通知、网络请求都可能失败。
- 测试时要先判断这是“预期限制”还是“真实缺陷”。
- 例如：
  - 未配置 Emby 时返回 `500`，如果文档和脚本已约定这是预期路径，就不应当当成回归失败。
  - 本地媒体源不支持某个 STRM 接口时，返回明确的 `400` 比静默失败更好。

### 3.5 中文文件名和标点差异要专门处理

- 中文片名、全角标点、空格、紧凑写法都可能影响识别结果。
- TMDB 搜索不能只依赖单一标题形态，至少要保留标题变体回退。
- 相关改动必须补中文样例测试，不能只测英文或纯数字片名。

### 3.6 页面按钮和弹窗逻辑要做回归

- 只改样式不代表安全，按钮状态、loading、关闭时机、遮罩释放都要测。
- “刷新预览后弹窗能否退出”“提交后按钮是否恢复可点”这类问题很容易漏。
- 前端改动后必须跑构建，并至少走一轮浏览器主流程验证。

### 3.7 异步预览和轮询必须可取消、可收口

- 任何“启动任务 + 前端轮询状态”的交互，都必须在弹窗关闭、页面切换、重新发起同类任务时立即停止旧轮询。
- 预览类按钮不要把整个弹窗长期锁死；候选加载、任务轮询、执行提交要拆分状态，避免一个 `loading` 同时控制遮罩和按钮造成假死。
- 轮询必须有明确终态和兜底退出：至少覆盖 `completed`、`failed`、任务不存在、超时四类场景，禁止出现永久停留在 `pending/processing` 的前端体验。
- 后端异步任务在异常、panic、任务数据损坏时也必须回写失败状态，不能让前端只能无限轮询。
- 这类修复必须补浏览器回归用例，至少覆盖“刷新预览后退出 loading”和“关闭弹窗后旧轮询停止，再次打开不继承旧状态”。

### 3.8 不能再出现中文乱码

- 源码、脚本、文档、日志、测试数据统一使用 UTF-8 编码。
- 新增或修改中文内容时，必须确认文件没有被错误转码成 ANSI、GBK 或其他编码。
- 终端、构建产物、测试报告里出现中文乱码，优先当作编码问题排查，不要先怀疑业务逻辑。
- 涉及中文文件名、中文日志、中文提示、中文测试样例时，必须做一次真实读写或真实展示验证。
- 如果某个工具链无法稳定处理中文，就不要继续沿用该写法，直接换成稳定的 UTF-8 流程。

### 3.9 密钥类配置禁止“展示值回写”

- 任何 API Key、Token、密码类配置，后端返回给前端时只能用于展示状态，不能把脱敏值当成可再次提交的真实值。
- 前端读取到脱敏后的密钥时，输入框必须清空或仅作为 `placeholder` 或说明展示，禁止把 `abcd****wxyz` 这类字符串写回表单模型。
- 后端保存密钥配置时必须额外校验：只要请求值包含脱敏特征（如 `****`），直接拒绝写库，并返回明确错误信息。
- 允许“只改附属配置，不改现有密钥”时，接口必须支持空密钥保留旧值，不能强迫前端回传一次旧密钥。
- 涉及密钥配置的改动，回归时必须覆盖 3 个场景：首次保存、刷新后再次打开页面、未改密钥只改其他字段后提交。

### 3.10 命名结果必须统一归一化

- 任何“重命名预览”“整理预览”“整理执行”链路，只要会生成新文件名，就必须在 service 层统一做文件名归一化。
- 禁止把“扩展名重复”“标题尾巴重复”“模板手写扩展名导致结果异常”这类问题留给前端展示层兼容。
- 修复命名问题时，至少补一条中文样例回归，避免只覆盖英文文件名。

### 3.11 二级确认弹窗必须走统一入口

- 禁止在业务页面分散直写 `ElMessageBox.confirm` 或 `ElMessageBox.alert`。
- 所有确认弹窗统一复用 `easy-strm-front/src/utils/ui/messageBox.js`。
- 涉及 `el-dialog` 内再次弹确认框的场景，必须回归验证层级、居中、遮罩与移动端可读性。

## 4. 开发流程约定

### 4.1 修改前

- 先找相似实现，不要凭空新造一套。
- 先确认改动会不会影响初始化、路由注册、响应结构、测试签名。
- 涉及核心流程时，先写清楚影响范围，再动代码。

### 4.2 修改中

- 优先做兼容最小化的改动，避免一次性大重构。
- 一个问题只改一个主因，不要顺手改太多无关逻辑。
- 涉及后端接口时，前端消费点必须一起检查。

### 4.3 修改后

- 后端改动后，优先跑后端测试。
- 前端改动后，至少跑构建和浏览器回归。
- 如果测试失败，先确认是不是测试代码本身过期，再判断业务代码是否真有问题。

## 5. 测试规范

### 5.1 必跑项

- 后端单元测试
- 前端构建
- 浏览器主流程回归
- 关键交互点专项回归

### 5.2 测试判断规则

- 只要是签名不一致、初始化失败、依赖未注入，就优先当作代码问题处理。
- 只要是外部服务不可用、账号未配置、接口返回预期错误码，就先按“预期异常路径”判断。
- 测试报告里必须明确写出“失败原因”和“为何失败可接受 / 不可接受”。

### 5.3 回归补测要求

- 修一个测试问题，必须补一条能防止复发的回归用例。
- 修 TMDB 识别问题，要补中文片名样例。
- 修初始化问题，要补启动链路验证。
- 修接口返回结构问题，要补前后端消费端验证。

## 6. 代码与接口约定

1. 后端接口返回结构尽量统一。
2. 业务逻辑优先沉到 service 层，controller 只做参数和返回包装。
3. DAO 只负责数据访问，不要混入流程编排。
4. 外部系统调用要保留明确错误信息，便于测试定位。
5. 新增字段时，domain、dao、service、controller、前端表单要一起对齐。

## 7. 文档与记录

- 重要测试问题、修复结论、回归结果要记录到项目文档。
- 文档要写清楚“问题现象、根因、修复方式、验证结果”。
- 不要只写功能介绍，不要只写理想状态。

## 8. 这次沉淀出来的通用坑

- 初始化位置不对，会把正常页面变成 500。
- 测试签名漏参数，会让整个包编译失败。
- 响应结构不统一，会把前端兼容写成永久负担。
- TMDB 识别只看一种标题写法，会在中文片名上翻车。
- 中文乱码通常不是“显示问题”这么简单，它会连带影响日志定位、测试断言、文件名识别和浏览器回归结果。
- 外部依赖失败如果不区分预期与异常，测试结论会失真。
- 按钮和弹窗只测打开不测关闭，最容易漏掉 UI 回归。

## 9. 执行要求

- 新增或修改功能前，先对照本文档检查一遍。
- 发现新坑后，优先补进本文档，而不是只修当前代码。
- 本文档优先作为全项目统一规范，不再按单个功能拆分说明。
