# 产品与架构

- 更新日期：2026-04-24
- 维护者：Codex
- 说明：本文档合并了原需求总览、路线图、信息架构、仪表盘重构方案等长期规划类文档，作为项目唯一的产品与架构入口。

## 1. 项目定位

easy-strm 当前定位为面向个人媒体库的整理与 `.strm` 生成工作台，核心目标不是单点文件处理，而是把媒体管理相关流程收敛到一个统一后台。

当前稳定主链路：

`媒体源接入 -> 文件浏览 -> TMDB 识别 -> 重命名预览 -> 整理执行 -> STRM 生成 -> 任务追踪`

## 2. 当前能力范围

### 已具备能力

- 认证与账号：登录、用户信息、115 账号管理
- 媒体管理：媒体源、本地/115 浏览、识别、重命名、整理、结果回看
- STRM：配置管理、任务生成、任务列表
- 自动化：本地监控、自动整理、统一任务中心
- 运维辅助：Dashboard、日志中心、网络测试、系统设置

### 当前边界

- 首要目标仍是把媒体管理主链路做稳定
- Emby 联动属于已接入能力，但不是当前文档整理后的唯一主线
- 多用户、插件化、复杂下载器与大规模资源站接入仍不在当前主范围内

## 3. 当前技术架构

| 层级 | 现状 |
| --- | --- |
| 前端 | `easy-strm-front`，Vue 3 + Vite + Element Plus |
| 后端 | `easy-strm`，Go + Gin |
| 数据 | PostgreSQL + Redis |
| 业务分层 | `domain` / `dao` / `service` / `controller` |

后端当前核心服务集中在以下方向：

- `media_source_service`
- `organize_service`
- `rename_service`
- `scrape_service`
- `strm_service`
- `watch_service`
- `task_service`
- `tmdb_service`
- `dashboard_service`

## 4. 现阶段产品主线

当前版本建议继续围绕 `MediaManager Beta` 方向推进，唯一主目标保持为：

`媒体源浏览 -> TMDB 识别 -> 重命名预览 -> 整理执行 -> 结果反馈`

### In Scope

- 媒体源与文件浏览体验完善
- TMDB 识别、手动修正、重命名与整理闭环
- 整理结果、失败原因、任务状态可观测
- 115 场景基础可用性与一致性修复
- 测试与回归补齐

### Out of Scope

- 全新下载器体系
- 复杂多用户权限
- 大规模插件化框架
- 超前资源搜索/榜单/订阅平台化能力

## 5. 页面与信息架构

当前仓库已形成的主要业务中心：

1. 系统与账号
2. 媒体处理
3. STRM
4. 任务与运维

建议继续按工作流而不是技术实现组织页面：

1. 仪表盘
2. 媒体管理
3. STRM
4. 115 与系统设置
5. 任务与日志

### Dashboard 的角色

- 负责全局导航和关键状态概览
- 不再承担“把所有业务都塞进首页”的职责
- 仪表盘首页应聚焦统计、任务、系统状态和快捷动作

### MediaManager 的角色

- 负责媒体源选择与上下文切换
- 负责文件工作区与批量操作
- 负责识别、整理、刮削、STRM 等动作入口

## 6. 当前技术债

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| TD-001 | 旧实现与新实现并存 | 维护成本高 |
| TD-002 | 部分模型与接口语义历史包袱较重 | 前后端联调成本高 |
| TD-003 | 文档曾长期按时间戳扩散 | 查找成本高 |
| TD-004 | 自动化能力与展示层仍有进一步统一空间 | 体验不稳定 |

## 7. 中期演进方向

如果后续继续扩展，建议按下面顺序推进：

1. 先稳住当前媒体管理主链路
2. 再强化统一任务编排与结果展示
3. 然后补资源视角的聚合页面
4. 最后考虑搜索、订阅、自动化增强等平台化能力
